# v1.4 Phase 2 — Executor Entry Adapter

Implemented 2026-09-14 in the development checkout, on top of the existing Phase 0
audit and Phase 1 dispatch migration. This slice stops at Executor entry. It does
not change Scheduled Automation transport or publication/completion packaging.

## Ownership change

[`executor_entry.py`](../scripts/executor_entry.py) owns task discovery, claim
acquisition, workspace preparation and the initial authorization checkpoint.
A fresh Executor wake runs one command from its configured Runtime:

```powershell
python scripts/executor_entry.py
```

The helper defaults to the Runtime installation containing its script; `--root`
is available for explicit embedding and isolated fixtures. It returns one JSON
object. Only `status: READY` **and exit 0** permit stage work. The Executor receives
the work to solve instead of reconstructing authorization from inbox and pointers.

Within the existing kernel-backed, reentrant Runtime fence mutex, entry:

1. Reconciles existing control transactions and selects `authorized_dispatch`.
2. Validates identity and the processed/retired state; applies the existing live
   authorization, archive/seal, control revision/pause, expiry, lifecycle, project
   and completion-ledger checks. An inbox alone never authorizes acquisition.
3. Reads the authorized inbox bytes, verifies their hash and complete identity,
   and prepares a semantic projection without changing the immutable wire.
4. Acquires through the existing permanent `mkdir` claim compare-and-set and token
   mechanism, or verifies a retained owner token on resume without acquiring.
5. Calls the existing fenced workspace preparation and checks authority again.
   Before returning, it also checks that the task bytes have not changed and that
   the completion-staging path passes the existing safe-path rules.

[`executor_claim.py`](../scripts/executor_claim.py) now exposes a structured
`ClaimResult` from `acquire_locked`. Its old CLI adapter still returns the existing
messages, exit codes and owner token. Entry does not launch helper subprocesses or
parse their stdout. Existing claim, fence and completion authority are reused;
there is no second authorization implementation or new durable authority file.

## Executor-visible result and behavior

The successful result has four useful parts:

| Field | Contents and purpose |
| --- | --- |
| `task` | Objective, inputs, outputs, criteria, limits, restrictions and stop conditions. Unknown semantic fields, custom protocol instructions and FV gate/policy/claim data are retained without truncation. |
| `attempt` | Original five-field identity, project ID, expiry and secret claim token. Identity remains available for the unchanged publication/completion contract. |
| `paths` | Absolute Runtime root, canonical project root, prepared attempt workspace and completion-staging root. Staging is not created by entry. |
| `capabilities` | Attempt-local candidate writes, canonical read-only inputs, publication roots/exclusions/size bound, existing helper names, and explicit `direct_canonical_writes: false` / `os_sandbox: false`. |

The view omits wire/model/scheduler metadata and removes only exact matches to the
16 canonical legacy `EXECUTOR_PROTOCOL` strings already covered by the permanent
prompt. It does not classify or discard arbitrary instructions by keywords. Custom
instructions remain in `EXECUTOR_PROTOCOL`; Final Verification metadata and its
generated result-format instructions survive. The full wire/archive stays intact
for validation, old clients and completion construction. This deliberately avoids
a wire-schema migration or semantic loss in compatibility tasks.

| Status | Exit | Behavior |
| --- | ---: | --- |
| `READY` | 0 | Return the attempt-bound view; execute this stage only. |
| `NO_WORK` | 10 | Valid Runtime state has no authorization and no candidate; stop quietly. |
| `DUPLICATE` | 10 | Existing permanent claim; no owner token or task view returned. Stop quietly. |
| `STALE_TASK` | 11 | Processed, retired or timeout-recorded attempt; stop. |
| `NOT_AUTHORIZED` | 12 | Authorization/fence failure, wrong resume token, damaged state, unavailable bound inbox, expired attempt or unsupported legacy acquisition; stop. |
| `ERROR` | 12 | Filesystem/operational error caught by entry; stop. |

All non-ready results contain only schema version, status, `action: STOP` and a
diagnostic reason. They contain no task or credential payload. Missing/corrupt
Runtime state fails closed rather than being interpreted as an empty inbox.
Expiry without a recorded retirement is an authorization failure. Invalid CLI
syntax is rejected by argparse with nonzero exit; the permanent prompt also
requires stopping on malformed output or command failure.

For continuation by the **same owning session**, including a restarted helper
process, the only additional input is its retained token:

```powershell
python scripts/executor_entry.py --resume-token "<retained claim_token>"
```

The token must match the current authorization's exact claim through the existing
constant-time hash comparison. A previous owner's token cannot acquire or adopt
a superseding task, even when that new task is unclaimed. Resume never falls back
to acquisition, scans for tokens, rotates a credential or extends the deadline.
A fresh overlapping wake has no token and receives no means to recover one.

An existing owner can continue under the existing safe-pause policy; a new claim
cannot. STOP, Human Review, retirement, expiry, supersession and completion retain
their existing fence behavior. If entry crashes or preparation fails after the
permanent claim is made but before the result reaches the owner, the claim stays
in place. Without a retained token, the Executor stops and the existing Runtime /
Supervisor timeout/retry path must supply a fresh identity. There is no claim reset.

## Before / after against the Phase 0 baseline

The baseline is the saved
[Phase 0 census](../evidence/v1.4-intelligence-overhead-audit/context-census.json)
for `v1.3.0` (`f1abe1ed688b2ec15aacc838cdb502ceb981d79d`). Phase 1 left the
Executor prompt and wire payload unchanged, so this also describes the entry
surface immediately before Phase 2.

| Executor responsibility | Before | After |
| --- | --- | --- |
| Find work | Read `TO_ZCODE.md`, identify candidate and extract five identity fields | Call entry; use READY task or stop |
| Acquire | Construct five-argument claim command and interpret helper outcomes | Runtime structured claim API |
| Resolve project | Read `control/ACTIVE_PROJECT.json` | Validated absolute paths returned |
| Prepare | Construct identity/token `prepare` call | Runtime prepares attempt workspace |
| Initial checkpoint | Construct identity/token `check` call | Runtime checks before returning READY |
| Startup protocol reference | Read `docs/STALE_WORKER_FENCING.md` | No required protocol/document read |
| Continue later | Preserve identity/token and run fence check | Reenter with retained token; later work-batch checks remain |
| Publish and complete | Hash files, publish, author staging/receipt, commit | Existing contract remains |

The shortened
[permanent prompt](../control/ZCODE_SCHEDULED_AUTOMATION_PROMPT.md) supplies entry,
resume and later-check commands. It no longer sends Executors to the inbox,
active-project pointer or fencing reference for startup. It retains the publication,
completion, FV, access-control and one-stage boundaries.

Run the read-only census with:

```powershell
python scripts/measure_executor_entry.py
```

[Captured comparison](../evidence/v1.4-executor-entry-adapter/context-comparison.json):

| Measured surface | Before | After | Reduction |
| --- | ---: | ---: | ---: |
| Permanent template characters | 16,053 | 14,609 | 1,444 (9.00%) |
| Bound permanent prompt characters | 16,089 | 14,657 | 1,432 (8.90%) |
| Required fencing-reference characters | 11,980 | 0 | 11,980 (100%) |
| Static reading surface: bound prompt + required reference | 28,069 | 14,657 | 13,412 (47.78%) |
| Same synthetic task: compact wire versus semantic task view | 3,730 | 336 | 3,394 (90.99%) |
| Canonical protocol instruction strings in that task view | 16 | 0 | 16 (100%) |
| Startup helper executions | 3 | 1 | 2 (66.67%) |
| Startup protocol-file reads by Executor | 3 | 0 | 3 (100%) |
| Startup identity argument values constructed by Executor | 15 | 0 | 15 (100%) |

The 15 argument values are five identity fields repeated across claim, prepare and
initial check. Token arguments are additional in the old flow and are not included
in that count. Runtime still performs the underlying reads/checks internally.

Using Phase 0's notation, **N** publications and **C** baseline explicit checks
(including the initial check, **C >= 1**) previously required **N + C + 3** helper
executions. Entry makes that **N + C + 1**: one entry, N publications, C−1 later
checkpoints (check or resume entry) and one commit. Startup's three document reads plus three helper executions
become one helper execution. Hashing, input copying, staging and substantive tools
remain outside this operation count. Helpers may share a shell call, so these
counts are not model turns.

These are BOM-stripped, LF-normalized Unicode character counts using the same
`<AUDIT_RUNTIME_ROOT>` substitution as Phase 0. The census verifies that the
compatibility task payload still exactly matches the saved baseline metrics before
comparing its projection. The fixture is small and does not represent a production
workload distribution. The 336-character task view excludes the returned identity,
credential, paths and capability envelope; it is **not** a claim that the complete
entry tool response is 336 characters. No total tool-output reduction is claimed.
Host/system prompts, tool schemas, history and subsequent turns remain unknown.
No provider tokens, actual ZCode latency or live deployment were measured, and no
character-to-token conversion is used.

## Compatibility and safety implications

- The existing claim CLI, token hashes, claim directories, fencing, decision
  receipts, exact dispatch archives/seals and authorization schema are unchanged.
  Old clients and new entry compete for the same permanent claim. New acquisition
  still requires archive/seal and current control revision. There is no authorization
  based on the projected task view alone.
- Archive-less recovery remains available only to an already claimed, fenced
  owner with its retained token under the existing recovery checks. Entry does not
  upgrade a tokenless or unfenced legacy attempt, manufacture a seal or mint a
  replacement token.
- All startup choreography uses the same lock as registration, retirement,
  publication and completion. The final view is a snapshot, not a reusable write
  authorization. Later checks and independent publish/commit checks remain required.
- Canonical project files remain read-only to the Executor. Candidate writes and
  subprocess output belong in the attempt workspace; only the existing Runtime
  publication helper writes canonical outputs. Safe-path traversal, symlink/reparse
  and hardlink protections remain. This is a cooperative **same-user filesystem
  boundary**, not an OS sandbox or protection against a malicious process with the
  same filesystem rights. Tokens must remain in the owning session; passing them
  through helper CLI arguments has the same host visibility limits as existing
  fence/completion commands.
- No live automation, provider, project or sibling Runtime was touched. Existing
  setup renderers pick up the repository prompt, but an operator must regenerate
  and replace the prompt installed in ZCode after updating Runtime code. Existing
  owning sessions should finish using their retained token and current instructions;
  do not treat deployment as a new claim. Automation scheduling/cadence and transport
  are unchanged, and no-work still entails an external wake.
- Phase 1 generated wires and FV/Human Decision compatibility wires keep their
  canonical protocol fields. The new Executor reads the projected view; old readers
  still see the legacy protocol. Removing that wire compatibility contract is not
  part of this slice.

## Validation

The focused suite in [test_executor_entry.py](../scripts/test_executor_entry.py)
uses isolated synthetic Runtime roots and real dispatch/archive/claim/fence code.
It covers successful entry through unchanged publication and completion, no-work,
unregistered candidates, duplicate wakes, processed/retired tasks, missing/damaged
authorization and inbox, malformed pointers, project-path and hardlink failures,
retained-token process restart, lost/wrong tokens, supersession, safe pause, STOP,
partial claims and preparation failures, legacy acquisition/recovery, and custom/FV
projection. Six concurrent OS processes produce one owner and five duplicate exits.
Failure results contain no task or credential. Claims remain permanent after failure.

Regression commands and final results are recorded in
[validation.txt](../evidence/v1.4-executor-entry-adapter/validation.txt).
The final full run passed **1,392 tests in 417.206 seconds, with 3 existing skips**
(clean checkout has no active project pointer). The Runtime-specific regression
passed **455 tests in 93.992 seconds, with no skips**, including the **23 entry
tests** and both setup renderers. The full run includes the final test-fixture fix:
one lifecycle poll now reads its state snapshot under the existing fence mutex,
avoiding a Windows read/replace race while preserving its assertions. Production
lifecycle behavior was not changed by that test fix.
The relevant suite includes ordinary dispatch, Supervisor/control/lifecycle,
authorization/claim/fence, completion/sealing, resume, Goal Anchor, Final Verification,
the Phase 0 census, and both automation setup renderers. The full repository suite
also exercises the console and productization paths.

## Next recommended migration

Phase 3 should move **publication/completion packaging** into Runtime: snapshot and
hash candidate outputs, build bound manifests and receipt identities, then call the
existing fenced publication/commit machinery. The Executor should provide semantic
findings, evidence references and honest outcomes. Preserve completion authority,
FV judgment boundaries and fail-closed handling. Broader context budgets, lifecycle
projection and wake/launch transport remain later work. Phase 2 stops here.
