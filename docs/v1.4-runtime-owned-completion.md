# v1.4 Phase 3 — Runtime-Owned Publication & Completion

Implemented in the development checkout on top of Phase 0–2. The Executor now
submits one semantic result to [`executor_finish.py`](../scripts/executor_finish.py).
Runtime derives artifact hashes, publication calls, manifests, receipt identity,
staging and the completion envelope. The existing publication fence and completion
commit/consume/seal machinery remain the authority. **A finish preparation is not
completion, and a successful task outcome is not Final Acceptance.**

This slice stops at Phase 3. Executor work capabilities, autonomy, checkpoints,
Supervisor context assembly, scheduling and transport are not redesigned. No live
Executor/provider call, automation update, deployment or production mutation was
performed. Existing Phase 0–2 changes in this development checkout were retained.

## Executor contract

After entry returns READY, the owner writes candidates in its attempt workspace
and one result file there, for example `finish.json`:

```json
{
  "artifacts": [
    {"path": "reports/summary.md", "role": "deliverable"},
    {"path": "evidence/check.txt", "role": "evidence"}
  ],
  "outcome": "PARTIAL",
  "findings": ["Two supplied sources agree."],
  "evidence": ["evidence/check.txt: comparison; input source A and source B"],
  "limitations": ["A third source was unavailable."],
  "completion": {
    "Acceptance self-check": ["Cross-check complete for two of three sources"],
    "Suggested memory updates": ["Third source remains unverified"]
  }
}
```

It invokes the Runtime helper once, using its retained owner token:

```powershell
python "<RUNTIME_ROOT>/scripts/executor_finish.py" --claim-token "<retained-token>" --result "finish.json"
```

`--result` is a forward-slash path relative to the owning attempt workspace, even
when the command runs from another working directory. The helper defaults to its
own installation root; `--root` remains available for embedding and isolated tests.
It derives the current identity/project from Runtime authorization and proves
ownership with the retained token. It never claims work, retrieves a lost token,
or adopts a newer dispatch using an older token. The Executor supplies no identity
arguments, timestamps, hashes, publication commands, manifests or staging path.

All six top-level result fields are required; unknown fields fail validation.

| Semantic field | Contract |
| --- | --- |
| `artifacts` | Actual produced files, each with exactly `path` and `role`. Role is `evidence`, `deliverable`, or `both`. Paths are identical beneath the attempt and canonical project roots. |
| `outcome` | `COMPLETED`, `PARTIAL`, `FAILED`, `BLOCKED`, `INCONCLUSIVE`, or `ABORTED_BY_USER`; copied faithfully to receipt `STATUS`. |
| `findings` | Semantic findings, mapped to receipt `Key findings`. |
| `evidence` | Semantic citations, mapped to receipt `Evidence pointers`. Existing inputs and URLs are allowed as references; Runtime does not certify their truth or claim it published them. |
| `limitations` | Actual limitations, mapped to receipt `Limitations`. |
| `completion` | Task-specific receipt fields, including acceptance self-check, suggested memory updates and FV results. Known Runtime envelope fields are rejected. Nested task data remains semantic data. |

The three text arrays permit zero to 100 nonempty strings, each at most 16,000
characters. Result JSON is bounded to 256 KiB, rejects duplicate object keys and
non-finite numbers, and must not contain the owner token. The fully constructed
receipt, including its FV envelope when applicable, is bounded to 64 KiB. This
checks actual serialized bytes on the new path; the legacy staging validator's
ineffective receipt-size expression is not changed by this slice.

Publication retains the existing roots `workspace/`, `evidence/`, `reports/`, the
`reports/USER_STATUS.md` exclusion, 64 MiB per-file limit, and rejection of
traversal, Windows aliases/ADS, symlinks/reparse points and hard links. Each manifest
is limited to 64 entries, with at most 128 artifacts total. `both` counts against
each manifest. Case-insensitive duplicates and overlapping paths are rejected.
No deletions, direct canonical writes or arbitrary Runtime Core publication are
added. Required-output satisfaction and substantive evidence quality remain
judgments; Runtime does not infer successful completion from filenames.

Every structured response has `schema_version: 1` and **`action: STOP`**:

| Status | Exit | Meaning |
| --- | ---: | --- |
| `FINISHED` | 0 | Publication and authoritative completion commit succeeded. |
| `ALREADY_FINISHED` | 10 | Matching completion already committed; read-only response. |
| `SEALED` | 11 | Matching completion already consumed or sealed; read-only response. |
| `NOT_AUTHORIZED` | 12 | Ownership, fence, control, archive or safe-path rejection. |
| `INVALID_RESULT` | 14 | Invalid semantic data, package, publication binding or integrity failure. |
| `ERROR` | 15 | Operational failure; a ledger commit may already exist. |

Only finish/replay responses include the commit ID; no response returns a token or
task contents. The permanent prompt directs immediate stop for every result,
command failure, malformed response or interruption. It no longer asks the
Executor to reconcile numeric completion-helper codes or the former contradictory
instructions about correcting invalid staging. Recovery belongs to Runtime and
Supervisor, and a fresh task retry still requires a fresh identity.

## Runtime construction and safety

The finish operation holds the existing reentrant, kernel-backed fence mutex
across discovery, preparation, publication and commit. It reconciles accepted
control transactions, validates the retained claim owner, checks for existing
ledger records (including damaged records), then uses `fence.check_locked` for
live authorization. Archive/hash, active project, retirement, expiry, lifecycle,
STOP/HUMAN_REVIEW and existing control-origin rules remain in force.

As before, safe pause or feedback pending after the current stage does not revoke
an already-running owner. Explicit interrupt, retirement, supersession and expiry
do. No stricter raw control-revision comparison is substituted for this existing
distinction. Every supported canonical replacement and completion commit still
rechecks its own live authority.

Before any publication, Runtime validates all semantic fields and FV result
structure, reads bounded candidate snapshots and computes their hashes, validates
all artifact/target paths and manifest limits, checks any existing publication
records against the supplied inventory, and validates generated staging paths.
An omitted or conflicting previous publication fails closed instead of silently
entering the completion manifest. Existing matching records also require intact
canonical bytes. Runtime never drops an invalid output and upgrades the result.

It creates one immutable preparation at
`handoff/executor_finishes/<completion-id>.json`, bound to the exact dispatch hash,
semantic-result digest, project/identity, generated timestamp, receipt and artifact
hash manifests. Its contents are bounded to 256 KiB. This is recovery data; it
does not grant write permission, authorize a dispatch or replace the ledger.
No token is stored there. Keep it with the existing Runtime history on restart.

For each new publication, finish calls the existing `executor_fence.publish`
with the Runtime-derived digest. That helper hashes its own copied snapshot and
rechecks authority immediately before canonical replacement. Matching publications
on replay are verified without replacing their files or publication timestamps.
Runtime then creates its staging under
`completion_staging/finish-<completion-id>/staging.json` and calls the existing
`executor_completion.commit`. Commit validates provenance, constructs the FV
envelope, seals the full publication manifest into the ledger, archives staging
and generates compatibility artifacts in the existing order.

The completion helper now has an optional `emit=False` structured-caller mode;
its default CLI output and exit behavior remain compatible. Claim-token validation
is factored into the fence module for reuse by live checks and read-only finish
replay. No new claim, dispatch, publication-record or completion-ledger schema is
introduced. Consume, seal, Goal Anchor and Final Acceptance implementations are
unchanged.

## Crash, restart and replay

Publication remains **atomic per file**, not a stage transaction. Canonical files
published before a failure remain legitimate partial outputs; finish does not
roll them back or call them completed. Recovery preserves the existing crash
window between canonical replacement and publication-record creation.

| Interruption boundary | Recovery behavior |
| --- | --- |
| Before preparation | No publication or completion; existing claim remains permanent. |
| After preparation, before/among publications | A retained owner with live authority can replay identical semantic results and candidate bytes. Changed data or hashes fail closed. |
| After file replacement, before its publication record | No completion; unchanged replay republishes through the fence and creates the missing record. |
| After publication records | Replay verifies matching canonical bytes and records, preserving provenance timestamps. |
| After staging creation | Replay verifies the existing staging matches the frozen preparation and continues through normal commit. |
| After ledger create, before archive/hints/response | Replay reports `ALREADY_FINISHED` without publishing or regenerating hints. Existing Orchestrator reconciliation repairs hints and consumes the committed entry. |
| After consume / seal | Replay reports `SEALED`; no completion rewrite or backward transition. |
| After retirement or a newer dispatch | Precommit replay cannot publish or finish with the old token. Preserve partial output for Supervisor review. |

The helper supports recovery of an interrupted finish; it does not automatically
schedule retries, reclaim attempts or authorize the Executor to repair a rejected
package. Recovery needs the original owner token and unchanged candidate files.
Lost tokens require the existing fresh-attempt recovery path. Once the matching
ledger exists, read-only classification can succeed without the original result
file; it never restores live work authority. A malformed, ambiguous or inconsistent
ledger prevents any new publication.

This remains a cooperative **same-user filesystem boundary**, not an OS sandbox.
The mutex serializes Runtime participants, but cannot intercept arbitrary direct
writes, hostile filesystem races, remote effects or detached processes. Hashes
bind observations and provenance, not truth. Frozen plans add durable IO and
bounded hashing under the existing lock; no Runtime performance improvement is
claimed. Large artifact batches can still cause existing lock contention limits.

## Final Verification and compatibility

For FV contract v1, the Executor supplies
`completion.FINAL_VERIFICATION_RESULTS`: overall status, exact claim rows, checks,
evidence pointers, auditor notes and applicable sandbox/isolation facts. Runtime
uses the verified archived dispatch and existing `construct_receipt` implementation
to create the identity/hash/policy envelope. It validates structure before
publication and again at commit; it never authors or promotes judgments. A negative
claim remains negative even when the Executor reports overall PASS. Existing
consume and terminal acceptance gates continue to reject it.

Entry retains all task semantics, FV gates and custom instructions. It translates
only the exact Runtime-generated FV staging instruction to the semantic finish
field name. The underlying instruction is factored into a constant without
changing generated wire bytes. The ordinary compatibility wire and canonical
protocol array remain unchanged. Custom protocol strings are never classified or
deleted by keyword.

Existing `executor_fence.py publish` and `executor_completion.py commit` remain
available to historical clients and recovery procedures. Fenced, already-claimed
archive-less ordinary work can use the new finish path under existing recovery
checks. Legacy FV without a verified v1 contract stays on the existing completion
compatibility API; finish rejects it explicitly rather than inventing a binding.
No historical archive, receipt, identity or publication record is migrated.

Deploy code and the regenerated [permanent Executor prompt](../control/ZCODE_SCHEDULED_AUTOMATION_PROMPT.md)
together using the existing setup renderer. Existing owning sessions keep their
retained token and existing compatible instructions. This work does not install
or change any live automation. Broader prompt/context redesign remains deferred.

## Before/after measurement

Reproduce the read-only census:

```powershell
python scripts/measure_runtime_owned_completion.py
```

The [captured comparison](../evidence/v1.4-runtime-owned-completion/context-comparison.json)
contains both complete task-equivalent fixtures and command strings. The saved
[Phase 2 prompt](../evidence/v1.4-runtime-owned-completion/phase2-executor-prompt.md)
is checked against Phase 2's recorded character/byte counts and hash before use.
Counts use the Phase 0 convention: BOM-stripped, LF-normalized Unicode characters
and the same synthetic Runtime root substitution.

| Surface | Phase 2 | Phase 3 | Reduction |
| --- | ---: | ---: | ---: |
| Permanent template characters | 14,609 | 13,806 | 803 (5.50%) |
| Bound permanent prompt characters | 14,657 | 13,860 | 797 (5.44%) |
| Two-artifact result JSON, same semantics | 928 | 454 | 474 (51.08%) |
| Same result JSON plus finish/publication commands | 1,554 | 534 | 1,020 (65.64%) |

With Phase 0's **N** published files and **C** baseline explicit checkpoints
(including the initial entry-owned check, C >= 1), required whole-stage helper
executions were **N + C + 3** in Phase 0 and **N + C + 1** after Phase 2. They are
now **C + 1**: one entry, C−1 later checkpoints and one finish. Finish-specific
helper executions fall from N+1 to 1, publication identity argument values from
5N to zero, Executor hashing from N to zero, and Executor staging/manifest/identity
copies to zero. Semantic artifact selection and evidence citations remain.

These are expected protocol operations and synthetic authoring surfaces, not
captured model turns, provider tokens or elapsed latency. Helpers may share one
shell call. Hashing and file IO still happen inside Runtime; scratch work,
substantive tools and host/system/history context are excluded. No total entry
tool-output saving is claimed. Provider token and latency savings are unavailable.

## Validation

[`test_executor_finish.py`](../scripts/test_executor_finish.py) covers real
dispatch/archive/entry/claim/fence integration, successful and unsuccessful outcomes,
receipt and publication provenance, invalid schemas/bytes/paths/limits, stale
authority, safe pause versus interrupt, concurrent finish processes, immutable
preparation replay, each publication/staging/ledger crash boundary, changed
candidates, damaged ledger/staging, missing hints, consume/seal and FV acceptance.
The measurement check also proves the before/after fixture preserves semantic
receipt contents and the new prompt removes hash/staging command requirements.

Final commands and regression results are recorded in
[`validation.txt`](../evidence/v1.4-runtime-owned-completion/validation.txt).
The full repository suite passed **1,419 tests in 428.000 seconds, with 3 existing
clean-checkout skips**. The Runtime-specific suite passed **492 tests in 99.086
seconds, with no skips**. Both include all **27 new finish/measurement/FV tests**
and the final implementation. Non-failing Windows console teardown warnings are
recorded in the validation evidence.

Phase 3 stops here. Supervisor context budgets, Executor capability/autonomy
redesign, lifecycle projection and host-owned wake/launch remain future work.
