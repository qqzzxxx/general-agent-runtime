# SECURITY

## Trust model

Three actors with different privileges:

- the **Orchestrator** is trusted machinery: it holds no credentials and calls no
  models, but it decides which agent may act next;
- the **Supervisor** is semi-trusted: it may direct work and terminate projects, but it
  cannot execute stages or publish executor tasks directly;
- the **Executor** is semi-trusted: it may do stage work inside one project and stage a
  *candidate* completion, but it cannot authorize itself, replay old tasks, touch other
  projects, or manufacture the authoritative fact that a task is complete.

Every privilege transfer between them is a mechanically verified file handoff. Neither
agent is trusted with bookkeeping: identity, authorization, claims, authoritative
completion, consumption, and sealing are owned by the Orchestrator and its two Runtime
helpers (`executor_claim.py`, `executor_completion.py`).

### Completion trust boundary (COMPLETION-SEAL-V1)

Only the Runtime-owned completion commit helper can create the authoritative fact
"this task is complete" (`handoff/completion_ledger/`, at most one entry per
MESSAGE_ID, monotonic `COMPLETION_COMMITTED -> COMPLETION_CONSUMED ->
COMPLETION_SEALED`, never reversible, restart-proof). The Executor produces only a
project-local staging candidate. Root `SUPERVISOR_BRIEF.md` /
`ZCODE_LAST_PROCESSED.txt` / `ZCODE_DONE.flag` are derived compatibility artifacts
generated by the Runtime; the Orchestrator never consumes a completion that is not
backed by a matching committed ledger record, so a late republish, a rewritten brief,
or a raw DONE hint cannot create or recreate a completion, cannot re-trigger a
Supervisor lifecycle decision, and is quarantined and audited instead.

## What protects what

| Threat | Mechanism |
|---|---|
| Task executed twice (automation double-wake, two executors) | permanent claim files, at-most-once, quiet exit 10/11 |
| Completion published twice (late republish after consumption) | Runtime-owned completion ledger; at-most-once commit per identity; consumed/sealed identities refuse forever (exit 10/11) |
| Rewritten root brief / pointer / DONE bypassing the helper | Orchestrator consumes only ledger-backed completions; unbound raw artifacts are quarantined + audited, never consumed |
| Completion committed while the Runtime is not waiting (wrong identity/lifecycle) | commit helper validates authorized dispatch, live WAITING_EXECUTOR state, and claim identity; mismatch fails closed |
| Old task replayed / identity forged | MESSAGE_ID retirement + NONCE binding + stale-identity rejection |
| Task injected by the executor side | dispatch authorization bound to inbox SHA-256; mismatch fails closed |
| Partial publication (crash mid-handoff) | ledger-first ordering; compatibility artifacts are Runtime-regenerable; restart reconcile repairs derived state |
| Two orchestrators on one runtime root | root-scoped exclusive lock + dead-owner-only reclaim, fail closed |
| Cross-project / cross-runtime interference | project scope validation under `ROOT\projects`; all state root-scoped; ledger entries carry PROJECT_ID |
| Agent bypassing the human on risky decisions | HUMAN_REVIEW lifecycle; decisions enter only via hash-bound receipts |
| False "project complete" | mechanical Final Verification gate before terminal COMPLETE |
| Runaway loops / token burn | budget ceilings, retry limits, no-progress redirect/stop rules, supervisor-turn caps |

## What must never be committed

The repository ships **no runtime state**. All of the following are gitignored and must
stay out of any fork or mirror:

- wire files and receipts (`TO_ZCODE.md`, `SUPERVISOR_BRIEF.md`, `FROM_ZCODE.md`,
  `ZCODE_DONE.flag`, `ZCODE_LAST_PROCESSED.txt`, `CODEX_LAST_OUTPUT.txt`);
- control-plane state (`.orchestrator.lock`, `orchestrator_runtime.json`,
  `ACTIVE_PROJECT.json`, `project_state.json`, `STOP`, `USER_ATTENTION.json`);
- claims and archives (`handoff/executor_claims/`, `handoff/archive/`);
- project data (`projects/*` — ship only the documented README), logs, task workspaces.

Reasons: execution history can contain proprietary research data, downloaded third-party
material (papers, images), machine-identifying details (usernames, hostnames, absolute
paths recorded in receipts and logs), and pre-release task content.

## Operational rules for operators

- Run each runtime root from its own directory; do not share `control/` between
  runtimes.
- Keep `RESEARCH_STATE.md` and project memory free of secrets: the runtime compresses
  and re-sends them to the Supervisor on every turn.
- Do not place credentials anywhere under the runtime root; stage work that needs
  credentials must go through HUMAN_REVIEW.
- Before publishing a fork or mirror, re-run the disclosure scan described in this
  document's checklist (grep the tree for key/token patterns, usernames, hostnames,
  absolute paths, and confirm `git status --ignored` contains no state files).
- A runtime root's `control/STOP` affects only that root.

## Known limitations

- Windows-first: the stale-lock reclaim uses the Windows process API; other platforms
  need a port of `_lock_owner_dead`.
- The Supervisor backend is invoked as a CLI subprocess with a fixed model policy; a
  malicious backend config could direct work outside project scope — the mechanical
  scope validation limits, but cannot eliminate, blast radius. Review launcher prompts.
- Scheduled automation runs with the user's privileges; treat the runtime root as
  user-trusted storage.
- COMPLETION-SEAL-V1 provides **protocol-level mechanical safety only**. On a
  single-machine, same-privilege model the Runtime assumes its own core and
  authoritative state (`orchestrator.py`, `scripts/`, `control/`,
  `handoff/completion_ledger/`) are not maliciously tampered with by an external
  process holding the same user's privileges. A same-privilege attacker could edit
  the ledger or the orchestrator itself. This release ships no OS ACLs, privilege
  separation, broker service, or OS sandbox; those are future work.
