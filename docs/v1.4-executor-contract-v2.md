# v1.4 Phase 4 — Executor Contract V2

Implemented in the development checkout on top of the completed Phase 0–3 work.
V2 makes the Executor responsible for an outcome, its acceptance evidence and
quality iteration. Runtime handles identity, acquisition, operation fencing,
candidate placement, publication, receipt construction and completion. The
canonical Scheduled Automation prompt now requests V2 explicitly. Historical V1
entry and completion APIs remain compatible.

This implementation is deliberately **filesystem-only**. The existing external
ZCode Scheduled Automation supplies no trusted API for Runtime to intercept or
sandbox its shell, network, browser or desktop actions. Advertising those as
enforced capabilities would be false. V2 supplies scoped file operations through
a Runtime adapter, denies unsupported capability requests, and describes the
remaining same-user host boundary honestly. HIGH autonomy changes how the model
works within its capabilities; it never creates more permissions.

Phase 4 stops here. No live automation, provider, project, deployment, scheduler,
host launch transport, Supervisor context-budget system or lifecycle redesign was
performed. Existing Phase 0–3 changes in this checkout were preserved.

## Architecture and ownership

The relevant starting designs are the [Phase 0 audit](v1.4-intelligence-overhead-audit.md),
[ordinary dispatch](v1.4-runtime-owned-dispatch.md),
[entry adapter](v1.4-executor-entry-adapter.md) and
[publication/completion adapter](v1.4-runtime-owned-completion.md).
After Phase 3, the permanent Executor prompt still contained 13,806 characters
and required the model to retain five identity fields and schedule explicit fence
checks before work batches. Deleting those checks without a replacement would
have weakened revocation behavior.

The implementation adds:

- [`executor_contract.py`](../scripts/executor_contract.py): validates execution
  preferences, declares the capabilities actually implemented, and projects the
  sealed task into a V2 outcome contract.
- [`executor_work.py`](../scripts/executor_work.py): performs bounded file
  operations and accepts semantic finish results. Each operation reenters the
  existing entry/fence path under the same reentrant Runtime mutex. Mutations
  recheck authority after snapshot IO and immediately before replacement.
- An explicit `--contract-version 2` path in
  [`executor_entry.py`](../scripts/executor_entry.py): returns the contract and an
  opaque session value, without identity fields, project IDs, absolute project
  paths, staging paths or helper-construction metadata.
- Optional `execution` preferences in the existing ordinary semantic proposal.
  Runtime validates them and copies normalized `EXECUTION` into the existing
  sealed dispatch. No new authority file or dispatch wire version is introduced.
- A rewritten [permanent prompt](../control/ZCODE_SCHEDULED_AUTOMATION_PROMPT.md)
  describing outcome ownership, task operations and honest results instead of
  the old protocol walkthrough.

| Responsibility | Executor | Runtime |
| --- | --- | --- |
| Outcome and approach | Interpret the brief; choose methods at the assigned autonomy | Validate and deliver the bound brief |
| Quality | Inspect results, improve weaknesses, evaluate criteria and cite evidence | Preserve submitted judgments without upgrading them |
| Capabilities | Use advertised operations; report missing capabilities | Check policy, scope, ownership and live authority on each operation |
| Identity and fencing | Retain one opaque session value as transport | Discover and validate identity; acquire once; check revocation/deadlines |
| Files and completion | Supply relative candidate paths, contents and semantic result | Place candidates; hash, publish, construct receipt/staging and commit |
| Next stage and acceptance | Report findings and gaps | Existing Supervisor and Final Acceptance gates remain unchanged |

The session value is the existing claim token, renamed at the V2 transport
boundary. It is not a new credential, permission file or authorization source.
It is still visible to the owning model/host and passed through CLI transport;
Phase 4 cannot hide it inside an unavailable host session API. The model need not
inspect it or derive anything from it. Lost tokens are not recovered, rotated or
reclaimed. A retained old token cannot adopt a newer dispatch.

## Outcome contract

A fresh wake runs:

```text
python "<RUNTIME_ROOT>/scripts/executor_entry.py" --contract-version 2
```

Only READY / exit 0 returns `{schema_version: 2, status, action, session, contract}`.
Non-ready V2 responses have `schema_version: 2`, `action: STOP` and diagnostics,
without task or credentials. Entry rejects a malformed V2 brief before acquisition.
The Python API and CLI default remain V1 for old clients; the installed V2 prompt
must select version 2. There is no automatic fallback after a V2 rejection.

The contract contains:

| Field | Content |
| --- | --- |
| `version` | Executor presentation version 2; distinct from existing wire and FV versions |
| `outcome` | The task objective the Executor owns |
| `context.inputs` | Selected task input descriptions/references; no whole-state or whole-Runtime injection |
| `context.task_data` | Unknown semantic task fields, retained without prefix truncation when present |
| `context.verification` | Only for supported FV: fixed claims, substantive policy, execution mode and result requirements |
| `deliverables` | Required output intent |
| `acceptance_criteria` | Explicit, nonempty criteria; preserved verbatim |
| `autonomy` | Validated level and the corresponding working style |
| `capabilities` | Actual filesystem operations/scope/limits and unavailable tool categories |
| `boundaries` | Task prohibitions, stop conditions, work budget and the few scope/isolation limits the model needs |

V2 removes known wire/identity/scheduler/model metadata and Runtime retry counters.
`MAX_RETRIES` continues to limit fresh dispatch attempts; it is not a cap on
candidate revision or quality inspection within an attempt. `MAX_TIME` is shown
as `work_budget_seconds`, a planning boundary. Existing authorization expiry,
project deadline, scheduler grace and watchdog behavior remain authoritative;
this phase does not add a new wall-clock budget timer or promise termination at
exactly MAX_TIME seconds.

Only exact canonical legacy `EXECUTOR_PROTOCOL` strings are recognized. V1 keeps
arbitrary custom protocol strings as before. V2 **rejects** unknown protocol
strings rather than deleting them by keyword or showing conflicting mechanical
instructions to the Executor. Reauthor their substantive requirements in inputs,
criteria, restrictions or semantic task context in a fresh dispatch. Unknown
semantic data is preserved, not silently classified as irrelevant. Context
selection remains the Supervisor's task-authoring responsibility; there is no
new relevance-ranking model, history summarizer or prefix budget in Phase 4.

## Autonomy and capability policy

The ordinary proposal's optional `execution` field uses this form:

```json
{
  "autonomy": "HIGH",
  "capabilities": {
    "filesystem": "workspace",
    "shell": "none",
    "network": "none",
    "browser": "none",
    "gui": "none"
  },
  "read_paths": ["inputs/product-brief.md", "workspace", "evidence"]
}
```

The six existing required proposal fields remain unchanged. Omission defaults to
NORMAL, filesystem `workspace`, other categories `none`, and project read paths
`workspace`, `evidence`, `reports`. Set `read_paths` explicitly for other inputs.
Paths identify an exact file or a subtree in the active project; natural-language
`inputs` strings are not interpreted as filesystem grants. Unknown keys, levels,
modes and unsafe paths fail validation. Full-wire compatibility tasks may carry
the same `EXECUTION` object; entry validates it before issuing a V2 view.

| Level | Method discretion and expected behavior |
| --- | --- |
| LOW | Follow the supplied approach, inspect and correct defects; report BLOCKED when a material method/scope decision is missing |
| NORMAL | Choose suitable methods, check every criterion and repair defects |
| HIGH | Explore relevant inputs, compare useful alternatives, inspect intermediate results and iterate when it improves the outcome |

All levels can repair defects. HIGH stops when criteria are met, improvement has
little further value, the work budget is reached or a hard boundary applies.
An unsatisfied criterion stays an explicit gap. This is working-style guidance,
not a mechanically enforceable guarantee that the model iterates or judges well.
Tests prove the three levels have identical capabilities for identical policy.

| Category | Shipped modes | Enforced scope / limitation |
| --- | --- | --- |
| Filesystem | `none`, `read`, `workspace` | `read` supplies scoped project/work reads and listing; `workspace` also supplies candidate write and copy. `none` requires empty read_paths. Runtime enforces these modes inside the adapter. |
| Shell | `none` | No arbitrary command execution adapter or subprocess sandbox |
| Network | `none` | No network client or enforceable network policy |
| Browser | `none` | No controlled browsing, rendering or interaction adapter |
| GUI | `none` | No controlled desktop/session adapter |

Read-only/none tasks can still submit findings with no artifacts. They cannot
publish a file even if an unmediated host writer placed it in candidate space.
Neither task prose nor an autonomy level can enable an unsupported category.
V2 cannot perform general builds, executable tests, live research, browser QA,
desktop automation or Runtime-core maintenance with this shipped adapter. Such
requirements must be reported as unavailable or use an explicitly maintained
historical integration outside V2; do not silently route them through host tools.

The external host still has whatever tools and OS rights it has. Runtime does not
disable those globally. The permanent contract requires the host command tool to
be used only as transport for entry/work, and the helper offers no arbitrary
command operation. Thus mediated path/mode/authority checks are enforced in code;
compliance with the mediation boundary is cooperative, as in Phases 2–3. There is
no claim of an OS sandbox, protection against hostile same-user processes,
interception of direct host writes, or cancellation of detached host activity.

## Task operations and completion

Send one JSON request on stdin to:

```text
python "<RUNTIME_ROOT>/scripts/executor_work.py" --session "<retained session>"
```

| Operation | Required fields in addition to `op` | Behavior |
| --- | --- | --- |
| `list` | `area`, `path` | Nonrecursive project/work directory observations, at most 1000 entries |
| `read` | `area`, `path` | UTF-8 project/work text, at most 256 KiB |
| `write` | `path`, `text` | Atomic replacement of a work candidate, at most 256 KiB UTF-8 |
| `copy` | `area`, `path`, `destination` | Bounded byte copy into work, at most 64 MiB; no shared inode |
| `finish` | `result` | Submit the six Phase 3 semantic result fields; Runtime creates the result file and calls existing finish |

`area` is `project` or `work`. Work paths are under `workspace/`, `evidence/` or
`reports/`, excluding `reports/USER_STATUS.md`. Project reads are restricted to
the declared read_paths and reject Runtime control/history/authority paths.
Traversal, absolute paths, Windows aliases/ADS, symlinks, reparse points and hard
links use the existing safe-path protections. Listing omits USER_STATUS; unsafe
links fail closed. Requests are bounded to 1 MiB, reject duplicate JSON keys,
unknown fields and non-finite numbers, and cannot contain the session secret.

`OK / CONTINUE / exit 0` returns a successful operation observation.
`UNAVAILABLE / CONTINUE / exit 0` means a permitted input is missing, oversized,
non-text or unsuitable for the requested observation. It has no success payload
and causes no task mutation; another permitted approach or an honest limited
result is allowed. An authorization, capability or path violation returns STOP.
Malformed requests and operational failures also stop; no automatic claim repair
or privilege expansion occurs. Every subsequent operation checks live authority
again, even after UNAVAILABLE.

The finish request is `{ "op": "finish", "result": { ... } }`. `result` keeps
Phase 3's required `artifacts`, `outcome`, `findings`, `evidence`, `limitations` and
`completion`. The Executor reports performed checks and remaining gaps in its
acceptance self-check. Runtime does not invent this assessment or promote a
negative outcome. V2 never asks for receipt identity, timestamps, hashes,
manifests, staging paths, per-file publication commands or numeric recovery codes.

Runtime freezes the submitted result in the attempt before calling Phase 3
finish. Further candidate operations through V2 are closed. Interrupted precommit
finish can be recovered with the same retained session and identical result;
changed results fail closed. Phase 3's frozen preparation, per-file atomic
publication, provenance, ledger and crash-window behavior remain intact. Every
finish response ends the Executor run. After commit, a V2 work replay fails its
live entry gate without writing; the underlying finish API still provides its
existing read-only ALREADY_FINISHED/SEALED recovery classifications. There is no
new completion authority or implicit next-stage dispatch.

Opaque URL-safe tokens can begin with `-`. Validation exposed an argparse edge
case in separated token arguments; entry, work and finish now normalize their
token option/value pair before parsing. Tokens and ownership semantics are
unchanged, and a deterministic leading-dash-token CLI test covers the fix.

## Final Verification and fail-closed behavior

V2 supports sealed FV contract v1 with LIVE_READ_ONLY execution. It exposes the
exact claims, allowed judgments, required checks and applicable policy constraints;
it omits policy IDs/versions, hashes, claim counts and completion identity binding.
The Executor supplies `completion.FINAL_VERIFICATION_RESULTS`, including exact
claim rows and honest negative/unverifiable results. Runtime derives the existing
FV envelope from the sealed dispatch. A reported overall PASS cannot override a
negative critical claim. Legacy FV gates and unsupported execution modes, including
SANDBOX_DESTRUCTIVE, are rejected by V2 rather than implying a sandbox exists.

The adapter reuses existing authorization, archive/seal validation, permanent
claims, ownership checks, project isolation, expiry, STOP/HUMAN_REVIEW, retirement,
safe pause versus explicit interrupt, publication and completion gates. A pause
that allows the running owner to finish still does so; explicit interrupt revokes
subsequent V2 operations. Mutation authority is checked again after candidate IO.
No new lock, identity allocator, authorization schema or durable policy grant was
created. Stored policy is bound by the same exact dispatch bytes as the outcome.

## V1/V2 comparison and iteration evidence

For this comparison, **V1 means the completed Phase 3 Executor surface**, not the
much larger original Phase 0 baseline or the numeric wire protocol version.
The [saved V1 prompt](../evidence/v1.4-executor-contract-v2/v1-executor-prompt.md)
is verified against Phase 3's recorded source hash and size. The
[saved V1 entry source](../evidence/v1.4-executor-contract-v2/v1-executor-entry.py)
preserves that implementation for review. The V1 projection and public APIs remain
executable. [Measurement code](../scripts/measure_executor_contract.py) uses the
same task and actual entry responses, normalizing only session, expiry and
absolute-path placeholders. It performs all dispatch/claim/publication tests in
private temporary Runtime roots.

Reproduce:

```text
python scripts/measure_executor_contract.py
```

[Captured comparison](../evidence/v1.4-executor-contract-v2/context-comparison.json):

| Normalized character surface | V1 | V2 | Change |
| --- | ---: | ---: | ---: |
| Permanent template | 13,806 | 5,335 | 61.36% smaller |
| Bound permanent prompt | 13,860 | 5,359 | 61.33% smaller |
| Task projection | 261 | 1,746 | 1,485 larger |
| Complete entry response | 1,064 | 1,836 | 772 larger |
| Bound prompt plus complete entry | 14,924 | 7,195 | 51.79% smaller |

Explicit capabilities/autonomy cost context. The total reduction comes from
removing the repeated permanent protocol, not from hiding the larger V2 view or
counting only its objective. These are BOM-stripped, LF-normalized Unicode
characters and compact JSON, not provider tokens. The fixture is small and not a
production task distribution. Host/system prompts, tool schemas, later request
payloads, tool output, history, context retention, process costs and Runtime IO
are not part of this surface total. No character-to-token conversion is used.

The UI case asks for a clear sign-up form with an associated label for every input
and a descriptive submit action. The first scripted candidate has neither; the
revised candidate has an associated Email address label and Create account button.
An independent HTML parser applies the same two structural checks to each
observed candidate and again to its canonical published bytes.

| Scripted scenario | Revisions / inspection | Structural checks | Committed outcome | Client fence calls |
| --- | --- | --- | --- | ---: |
| V1 stage-only control | First candidate inspected and submitted with gaps | 0/2 | PARTIAL | 2 |
| V1 iterative control | First candidate inspected, revised and reinspected | 0/2 → 2/2 | COMPLETED | 3 |
| V2 HIGH iterative | Same candidates and checks through write/read operations | 0/2 → 2/2 | COMPLETED | 0 |

The stage-only control shows why producing a file alone is insufficient. It is
not a captured V1 model behavior. The V1 iterative control reaches **identical
final source, judgments and semantic result** to V2. In that matched workflow,
V1's three explicit fence calls require 15 identity argument values; V2's checks
are inside its operations. Both preserve publication provenance. V2 makes this
iteration an explicit responsibility and supports it without model-managed
checkpoints; the experiment does not show that V1 was incapable of iteration.

All edits, choices to revise and judgments in this experiment are scripted.
**No model-quality improvement was measured or is claimed.** There is no live
model A/B, trusted Executor telemetry, provider token saving or latency result;
those fields are null in the evidence. The checks establish only two HTML source
properties, not visual design quality, browser rendering, functional submission,
accessibility certification or real user success. Those limitations remain in
the committed receipt. Tasks requiring those checks must report the unavailable
capability; the sample's acceptance criteria intentionally cover source properties.

## Validation and rollout

The [Phase 4 tests](../scripts/test_executor_contract.py) cover outcome projection,
unknown semantics, unknown/custom protocol rejection, autonomy defaults, capability
denials, explicit read scopes, bounded operations, unavailable-input alternatives,
unsafe paths/hardlinks, private candidate work, semantic finish/provenance,
read-only publication denial, token privacy and leading-dash CLI transport,
duplicate/resume ownership, retirement/supersession, pause/interrupt, authority
expiry during candidate IO, interrupted finish recovery, FV judgments and the
scripted UI controls. Ordinary dispatch tests additionally verify normalized
policy archiving and rejection of changed dispatch bytes or unsupported policies.

Final regression results and reproduction details are recorded in
[validation.txt](../evidence/v1.4-executor-contract-v2/validation.txt).
The final full repository run completed **1,440 tests in 425.968 seconds, with
3 existing clean-checkout skips** and no failures. It covers the final code and
all 21 tests added in Phase 4. The focused contract suite passed all 20 tests.
Non-failing file/subprocess/socket cleanup ResourceWarnings are recorded in the
validation evidence; no unrelated cleanup behavior was changed.

Deploy code and the regenerated permanent prompt together through the existing
setup renderers when separately authorized. Existing owners retain their token
and V1-compatible instructions. Before using V2, ensure the task has explicit
criteria, supported input scopes and capabilities, and no unresolved custom legacy
protocol or unsupported FV mode. The current host integration cannot enforce more
tools merely by adding names to a policy. Adding actual tool adapters or trusted
host launch/session binding is further work, not a completed Phase 4 capability.

No live prompt was installed and no active Runtime was migrated. Stop point:
**Phase 4**.
