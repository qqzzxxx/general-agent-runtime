# v1.4 Phase 8 — Supervisor V2

Implemented in the v1.4 development checkout on top of completed Phases 0–7.
The Supervisor now owns the user's outcome, quality and next valuable decision.
Context V2 replaces the old overlapping, prefix-truncated prompt with complete
decision records, current evidence and explicit references to full records.

**Stop point: Phase 8. No deployment, automation change or new live model run.**
The A/B analysis below uses the actual first implementation dispatches supplied by
the user. The V2 delegation is an authored counterfactual, not a sampled model
response. No model-quality or final-product improvement is claimed.

## Problem and evidence

The [Phase 0 audit](v1.4-intelligence-overhead-audit.md) identified repeated
goal/state/history/receipt material and arbitrary prefix cuts. Phase 1 moved
ordinary task construction into Runtime. Phases 2–7 moved Executor entry,
publication, completion, capability use and semantic finish recovery into their
current boundaries. This phase preserves those mechanisms.

The old Supervisor still received protocol-heavy instructions and both role
guides, plus broad state and memory on every fresh invocation. Its general
guidance required revision of only the broken part. For a product task, that can
elevate the current implementation into a requirement even when the user asked
for ownership of the complete experience.

The exact shared UI Goal says to improve the supplied console into a polished,
clear and usable product, preserve its information and intended actions, own the
final experience, and inspect/improve it before completion. It does not require
the existing layout, wording, DOM or JavaScript structure.

The user explicitly authorized read-only inspection of the shared sources and
two A/B Runtime archives outside this checkout. Only the named Goal, original
fixture files, first implementation dispatches and archive metadata, and the
projects' profile/Goal binding fields and canonical Goals were read. The `polished` directory was not used. Copies and source provenance are in
[ab-inputs](../evidence/v1.4-supervisor-v2/ab-inputs/sources.json).

These are **textual restrictions**, not proof that either run's final UI was bad.
Both briefs retain meaningful outcome ownership and neither explicitly freezes
the entire information architecture. However, the rename prohibition and B2's
presentation-only escape condition can constrain restructuring and semantic
relabeling that would otherwise preserve functionality. HIGH does not cancel an
explicit prohibition. Dependency restraint can be a reasonable implementation
choice for this static fixture; it is not an explicit user requirement in this Goal.
The dispatches do not establish why the Supervisor added these restrictions, or
that they caused any observed product-quality difference.

## Outcome ownership and delegation

[CODEX_SUPERVISOR_RUNTIME.md](../control/CODEX_SUPERVISOR_RUNTIME.md) is now the
compact canonical Outcome Owner policy. It distinguishes:

| Category | Meaning | UI example |
| --- | --- | --- |
| Desired outcome and quality | Result and experience to achieve; observable success | A mature console where status, work and next actions are easy to understand |
| Hard constraints | Actual user, Runtime, policy, compatibility or resource boundaries, with sources | Preserve supplied information and intended action meaning |
| Current implementation facts | Observations about the existing artifact | Static local HTML/CSS, inline handlers, many tables on one page |
| Revisable assumptions | Inherited interpretations or method choices | Table layout, section order, labels, navigation and DOM/JavaScript structure |

Preserving information means maintaining meaning and availability, including
discoverable detail views when appropriate. Preserving functionality means
maintaining intended behavior. Neither automatically freezes the implementation.
The policy permits regrouping, relabeling, navigation changes and progressive
disclosure when they serve the outcome and retain the required information and
actions. It does not select a particular design for the Executor.

The GENERAL guide no longer requires a local repair for every weak outcome. The
SOFTWARE_ENGINEERING guide distinguishes a bounded defect from product redesign.
Reproduction, compatibility and integrity evidence remain in place. Revision
scope follows the cause and desired result; unrelated work remains excluded.
HIGH is recommended for open-ended product/design work; LOW needs a concrete
reason to prescribe a method. Capability and authorization policy are unchanged.

The ordinary proposal accepts an optional `outcome_context` with exactly:

```json
{
  "desired_outcome": "The user's ultimate result, relative to this task.",
  "quality_bar": ["Observable experience or quality expectations."],
  "hard_constraints": [
    {"constraint": "An actual requirement.", "source": "Goal section or policy reference."}
  ],
  "current_facts": ["An observation about today's implementation."],
  "revisable_assumptions": ["A choice the Executor may reconsider."]
}
```

The field is optional for compatibility. If present, all five keys are required;
strings must be nonempty and at most 16,000 characters; arrays may contain at most
100 entries. Constraint entries require exactly `constraint` and `source`.
Unknown keys, malformed types and missing provenance fields fail before candidate
reservation. Runtime validates structure, not whether a model's source attribution
or judgment is correct. This context creates no authorization or capability grant.

[ordinary_dispatch.py](../scripts/ordinary_dispatch.py) carries it as
`OUTCOME_CONTEXT` in the existing sealed task. The unchanged Executor V2 projector
already retains semantic fields under `context.task_data`, so it delivers this
structure without any Executor code, capability or finish behavior change.
Required proposal fields, defaults, retries and Runtime identity construction
remain the same. Older proposals and already-archived tasks remain valid.

The [UI V2 example](../evidence/v1.4-supervisor-v2/generated/ui-v2-proposal.json)
preserves the exact Goal's information/action requirement and explicitly leaves
layout, copy and implementation open. It checks the real fixture behaviors:
Pause/Resume state, individual acknowledgement, review-all, disabled states and
activity feedback. It asks for rendered/interaction evidence and an overall UX
judgment, without prescribing a component layout or helper sequence. Outputs use
supported Runtime publication paths under `workspace/` and `evidence/`.

A [bounded compatibility counterexample](../evidence/v1.4-supervisor-v2/generated/fixed-constraint-proposal.json)
keeps a public button ID because the synthetic user explicitly requires it.
V2 preserves such a real implementation constraint. Freedom to redesign is not
permission to ignore stated interfaces or remove required data/actions.

## Context V2 selection and references

[supervisor_context.py](../scripts/supervisor_context.py) is a deterministic
presentation builder. It performs no model summarization, semantic relevance
ranking, lifecycle commit or authority update.

| Decision question | Delivered material |
| --- | --- |
| What is the user ultimately trying to achieve? | Full canonical Goal text, with existing verified Goal Anchor facts |
| What changed? | Current Runtime event and each verified intervention once; Human Decision receipt only in its special transaction block |
| What is true now? | Current state projection, task semantics and retry-relevant facts, latest history decision once, current project memory, Supervisor domain guide |
| What remains unresolved or weak? | Previous unmet-criteria assessment, explicitly requiring reassessment, plus current memory and latest untrusted receipt findings/limitations |
| What decision is needed? | Event-specific decision request; exact dispatch-repair error/budget when present; applicable Human Decision contract |

Selection rules are explicit:

- The entire Goal survives, including late requirements. There is no prefix cut.
- `decision_history` and the Human Decision consumption ledger remain in the
  referenced state file. The history tail is shown once; a differing latest-decision
  mirror is exposed as a conflict rather than silently preferred or discarded.
- Known task transport fields are omitted. Unknown current-state and receipt
  semantic fields remain visible. Missing values are not inferred as success.
- The previous unmet-criteria text appears once in the unresolved section, with a
  cross-reference in the decision view. It is a previous assessment, not new truth.
- Goal binding, dispatch repair and current receipt material have separate homes.
  Exact duplicate FV result fields are removed from the duplicate envelope; negative
  judgments, unknown fields and disagreements remain visible.
- A Runtime-supplied committed receipt takes precedence over the mutable root
  brief. A fallback root brief is explicitly unverified, untrusted compatibility
  evidence. The existing pre-invocation consume/validation gates remain authoritative.
- Only the Supervisor domain guide is injected. The Executor guide and full FV
  policy are referenced for targeted inspection.
- Current memory is organized under outcome, quality, constraints, facts,
  assumptions, unresolved questions, failed methods and human steering headings.
  Legacy/unrecognized prose remains complete. After the Supervisor reorganizes
  memory and adds `<!-- supervisor-context-v2: current-memory -->`, only H2 sections
  titled `Archive`, `Decision history` or `Historical decisions` are deferred,
  with their heading and line reference. Headings inside fenced examples do not
  become sections. Active requirements/steering must remain in current sections.

This is an event-relative decision view, **not an exhaustive diff since the last
committed decision**. No earlier snapshot means no invented change summary.
Current memory and evidence provide the basis for the Supervisor's judgment.
Unknown or oversized semantic material is never silently removed to meet a target.
Consequently V2 has no guaranteed total prompt budget; a large Goal or unstructured
legacy memory can still be expensive. Safe memory organization and targeted reads
remain necessary. The generated view does not assert that every projected fact is
correct, or that every model will identify the right constraints.

Full records remain at their original paths, with source sizes/hashes and delivery
descriptions in the prompt. Reads of text sources within one build are reused for
their source facts. No new authoritative file, summary cache, state migration or
durable decision-memory schema was introduced. Before applying a decision, the
Supervisor must read current state and preserve unshown fields/history; serializing
the view as replacement state is explicitly forbidden. Relevant history remains
available for retries, unresolved dependencies, contradictions and AUDIT.

The actual prompt carries its own character/UTF-8 counts, SHA-256 and section sizes
into the existing bounded turn observation. `invoke_codex` records these facts
from the same string sent on stdin, without rerunning the old file census. No
prompt/evidence content or claim credential is placed in the observation. The old
manifest helper remains available for compatibility; normal invocation uses V2.

## Preserved Runtime boundaries

The changes are confined to Supervisor presentation, optional semantic delegation
data, associated profile guidance, tests and documentation. Runtime still owns
deterministic task construction and all existing physical protocol authority.

Goal Anchor, control revision, pause/interrupt, decision receipt, exact archive/seal,
registration, permanent claim, stale-worker fencing, publication, completion
commit/consume/seal, retry budgets and restart recovery are unchanged. Context and
proposal presence never make a candidate executable. A changed `OUTCOME_CONTEXT`
invalidates the bound dispatch bytes just like a changed objective.

Final Verification still requires the bound policy and exact acceptance identity;
negative evidence is not promoted to PASS. Fixed claims and their standards remain
fixed. [SUPERVISOR_PROTOCOL_REFERENCE.md](../control/SUPERVISOR_PROTOCOL_REFERENCE.md)
retains the full-wire FV and Human Decision contracts for the turns that need them.
The verified Human Decision block and read-only structured transaction are retained;
receipt reading does not consume it. Ordinary proposals continue rejecting FV
fields. This phase does not migrate the remaining special full-wire output paths.

Executor V2's native tools, restrictions, working locations, checkpoints,
publication, semantic finish correction and immutable finish boundaries remain
unchanged. The existing cooperative same-user host-tool assurance limit remains.

## Measured comparison

Reproduce entirely offline from saved local evidence:

```powershell
python scripts/measure_supervisor_context.py --output evidence/v1.4-supervisor-v2/generated
```

The [comparison JSON](../evidence/v1.4-supervisor-v2/generated/comparison.json)
and full paired prompts are saved together. The pre-change Phase 7 builder,
canonical contract, ordinary-dispatch source and modified profile guidance are
frozen in the evidence directory. Each pair uses identical Goal, state, memory,
event and steering input. The UI bootstrap uses the exact shared Goal text, original HTML/CSS bytes,
and the SOFTWARE_ENGINEERING profile used by both recorded runs. Other cases are synthetic, including the serialized FV
receipt used only to compare presentation. The real ledger path is tested separately.

Counts are LF-normalized Unicode characters, with fixed time/nonce and normalized
temporary Runtime paths. These are not provider tokens. Host instructions, tool
schemas, later full-record reads, output/history retention, process overhead and
Executor execution are excluded.

| Matched prompt | Phase 7 | V2 | Reduction |
| --- | ---: | ---: | ---: |
| Summary bootstrap | 20,393 | 16,047 | 21.31% |
| Exact shared UI Goal bootstrap | 20,890 | 16,624 | 20.42% |
| UI history and steering | 57,129 | 17,589 | 69.21% |
| Long Goal with late success criterion | 32,387 | 33,204 | −2.52% |
| FV result | 21,173 | 16,835 | 20.49% |
| Timeout | 20,460 | 16,146 | 21.09% |
| Dispatch repair | 21,864 | 16,459 | 24.72% |

The long-Goal V2 prompt is larger because it preserves a late requirement that
Phase 7 omits. The history/steering case retains the latest decision without
injecting historical records and delivers the steering text once instead of twice.
The delivered role/delegation contract bodies total **11,925 → 9,525 characters**
(20.13% reduction). That subtotal excludes Goal Anchor, profile, scope, closing
instructions and delimiters; it includes valuable semantic guidance and is not a
measurement of pure protocol waste.

| Delegation surface | A recorded | B2 recorded | V2 authored example |
| --- | ---: | ---: | ---: |
| Compact substantive fields, including execution preferences | 3,754 | 3,172 | 2,966 |
| Acceptance criteria | 10 | 7 | 4 |
| Forbidden-action entries in the compared surface | 6 | 7 | 3 |

V2's example has one sourced preservation constraint in `outcome_context` and
three Runtime-supplied baseline prohibitions. It authors no extra forbidden-action
entries. The comparison adds the exact Runtime baseline restrictions before
projecting V2, so it does not compare a bare proposal against sealed tasks while
omitting their baseline. Capability policy also remains in force. Its normalized
proposal is 2,909 characters, and its complete Executor V2 task view is
7,301 characters. Explicit
context/capabilities add bytes. Fewer checklist entries are not themselves a
quality metric. The substantive comparison excludes wire identity, generated
protocol and scheduler metadata on all sides, while retaining any protocol prose
that the recorded Supervisor embedded in substantive fields.

The defensible improvement is in the **available solution space and the contract**:
the V2 example leaves organization, wording and implementation open while keeping
the user's required meanings/actions. It is not evidence that a live V2 Supervisor
will choose a better delegation or that its Executor will produce a better UI.
Provider-token savings, latency savings and model-quality improvement are null in
the captured evidence. A live matched run would be needed to evaluate those claims.

## Validation and stop point

Targeted tests cover complete late Goal/memory requirements, history-tail selection
and conflicting mirrors, deferred-history references, fenced Markdown examples,
single-copy steering/AUDIT, negative/unknown/conflicting receipt data, a real
committed receipt winning over mutable root text, exact prompt observations,
optional context validation, actual authorization before entry, unchanged capability
restrictions and tampered-dispatch rejection. Existing presentation expectations
were updated where Executor guidance and full FV mechanics moved to references;
mechanical lifecycle/FV assertions were retained.

Validation results are recorded in
[validation.txt](../evidence/v1.4-supervisor-v2/validation.txt).
The final full repository regression completed **1,499 tests in 550.625 seconds,
with 3 skips and no failures**. The final focused run passed **256 tests** across
Supervisor context/control, Goal Anchor, Human Review, dispatch, Runtime creation,
Executor V2, host-native execution and semantic finish recovery. An initial full
run found one stale documentation-location assertion; its exact nested FV checks
were retained against the new reference and the complete rerun passed. Non-failing
Windows cleanup warnings remain recorded in the logs.

No source project, A/B Runtime, shared fixture, live model, Executor automation,
provider configuration or scheduler was changed. Deployment must ship the new
Supervisor module, canonical contract and protocol reference together. Ordinary
projects need no state migration. Work stops at **Phase 8**.
