# v1.4 Phase 7 — Semantic Finish Validation & Recovery

Phase 7 fixes the Phase 5 failure in which V2 saved an FV result before validating
it, then refused the owner's corrected submission because the saved file existed.
The permanent claim survived, but its owner could no longer finish the attempt.

## Boundary and recovery

`executor-result.json` is now a replaceable attempt-local candidate. Its existence
does not mean validation succeeded, publication started, or completion occurred.
This also handles an old invalid Phase 5 cache without deleting or reacquiring its
claim, provided its original owner is still authorized and no durable boundary
exists.

The immutable boundary remains the atomic creation of the existing Runtime finish
plan under `handoff/executor_finishes`. Before creating it, Runtime validates the
semantic result, constructs and validates the FV receipt against the archived
claims and policy when applicable, bounds receipt/staging sizes, checks artifact
paths and bytes, checks publication policy and existing provenance, and checks
staging consistency. It rechecks live ownership before creating the plan. The plan
pins the result hash, artifact hashes, dispatch hash and staging timestamp before
any canonical publication or completion effect.

The V2 adapter no longer treats its earlier result-file write as that boundary.
On `INVALID_RESULT`, while still holding the Runtime mutex, it rechecks the live
claim owner and the durable boundary. Only when both checks allow correction does
it return:

```json
{"schema_version":2,"status":"INVALID_RESULT","action":"CORRECT_AND_RESUBMIT","reason":"…validation defect…"}
```

The same retained session may correct the result, inspect or repair candidate
files, stop candidate writers, and resubmit within the original scope and deadline.
This grants no new task, claim, deadline, retry budget or publication permission.
The helper's nonzero CLI exit must be interpreted with its structured response;
the permanent Executor prompt now describes this explicit exception to stopping.
Malformed requests, denied authority and other STOP responses still stop the run.

Entry's `candidate_work_open`, mediated work and inspection use one shared durable
boundary check. An existing plan, finish staging, publication directory or matching
ledger entry closes candidate work. These markers are checked conservatively by
presence, including damaged records; corruption never authorizes reopening.
Recovery never removes them. Result caches are rewritten only before this boundary,
under the existing mutex and owner fence.

## Immutable completion behavior

- A crash before validation or plan creation leaves a correctable candidate.
- A valid plan is immutable even if the process crashes before its first output
  publication, or the result has no artifacts. Replay must retain the same result
  and candidate bytes.
- After publication, existing provenance and canonical hashes must match replay;
  a changed judgment, omitted publication or changed artifact cannot overwrite the
  prepared package.
- Completion still uses the existing commit ledger, consume and seal machinery.
  Direct finish ledger replay remains read-only (`ALREADY_FINISHED` / `SEALED`).
  V2 entry can instead stop an already completed session as no longer executable.
  Neither path republishes or recommits a changed result.
- A duplicate wake still receives `DUPLICATE` without the owner's session. A wrong,
  expired, interrupted, retired or superseded owner cannot use correction to gain
  authority. Validation errors themselves confer no right to resume.

The publication fence's crash and provenance rules are unchanged. In particular,
FV will not adopt an unrecorded canonical file merely because its bytes match a
candidate. A crash inside FV publication after canonical creation but before its
provenance record can still require existing watchdog/operator recovery; it has
already crossed the publication boundary and is not a schema-correction case.

## Semantic FV input

V2 now advertises a top-level `verification` field in the semantic result. Its six
existing base fields remain required. For example, the FV portion is:

```json
{
  "verification": {
    "overall_status": "INCONCLUSIVE",
    "claims": [
      {
        "claim_id": "C1",
        "status": "NOT_VERIFIABLE",
        "checks": {},
        "evidence_pointers": [],
        "auditor_note": "The supplied source was inaccessible; the claim could not be checked."
      }
    ]
  }
}
```

Submit one row for **each** fixed dispatched claim; the example shows a single row
only. `overall_status` is PASS, FAIL or INCONCLUSIVE. Claim statuses and substantive
checks come from the bound policy. Each row has exactly `claim_id`, `status`,
`checks`, `evidence_pointers` (a string array), and `auditor_note` (nonempty text).
Optional `sandbox` observations and boolean `isolation_incident` are retained when
provided; they cannot grant an execution mode. V2 continues to support only its
existing LIVE_READ_ONLY FV mode.

Runtime translates this input into `FINAL_VERIFICATION_RESULTS`, then constructs
the existing `FINAL_VERIFICATION` envelope with the immutable task identity,
dispatch hash, policy metadata, claims hash and execution mode. The V2 projection
and permanent prompt no longer require the Executor to author those completion
container names. Runtime rejects conflicting legacy and semantic FV inputs,
unknown semantic envelope fields, malformed rows, incomplete/duplicate claim
coverage, and FV judgments submitted for ordinary tasks.

Schema validity is separate from acceptance. Runtime does not fill missing claim
judgments, manufacture evidence, upgrade negative checks or require a PASS verdict
to commit. A valid negative/inconclusive result or isolation incident is committed
immutably and evaluated by the existing acceptance gate, not returned as a defect
to repair into a passing verdict.

## Compatibility and validation

The historical `completion.FINAL_VERIFICATION_RESULTS` finish input remains
supported with its existing validation and receipt shape. V1 task projection and
the low-level legacy FV completion API remain unchanged. No historical receipts,
archives, claims, authorization records or ledger entries are migrated.

`scripts/test_semantic_finish_recovery.py` exercises real sealed FV dispatches and
retained V2 sessions: invalid-then-corrected submission, original claim preservation,
duplicate wake, inspection/work reopening, legacy invalid caches, fresh-process
replay, missing artifact repair, immutable plan and publication boundaries,
changed artifact bytes, damaged markers, stale owners, interruption during
validation, semantic FV projection, legacy compatibility, and negative/incident
acceptance behavior. Ordinary schema recovery and native-resume boundary tests
are covered in the existing Executor suites. The original finish fault-injection
suite covers plan/publication/staging/ledger crashes, concurrent at-most-once
completion, retirement, provenance, and consume/seal.
