# Stale worker fencing (EXECUTOR-FENCE-V1)

## Incident and invariant

The incident was `700110 / attempt 1` acquiring its permanent claim, pausing for
hours, timing out while Runtime remained alive, and resuming after the Supervisor
dispatched `700111 / attempt 2`. Both workers could write the same U1–U3 outputs.
A duplicate wake for 700111 was correctly refused with `CLAIM_EXISTS`.

The defect was between claim and completion: `executor_claim.acquire` checked the
authorized identity and inbox hash once; stage writes had no Runtime gate.
`executor_timeout_event` only saved `timeout_notified_for_nonce`, without retiring
the identity. Replacement of `authorized_dispatch` affected future claims and
completion checks, but did not revoke an already running worker's filesystem IO.

The invariant is now: a claim is permanent acquisition history, not a permanent
write capability. Every supported canonical output publication requires a fresh
check of the exact live attempt and its claim-owner token, serialized with
retirement. Startup reads mutable Runtime state only after acquiring Orchestrator
ownership, preserving persisted retirement and pending timeout state even when a
starter was delayed. With that Runtime-owned state intact, restart cannot
reauthorize a retired attempt. Claims are never removed, renewed, or transferred.
Retry requires fresh MESSAGE_ID and NONCE.

## Mechanical boundary

All newly registered dispatches carry Runtime-owned `FENCE_VERSION=1`,
`PROJECT_ID`, and `EXPIRES_AT` in `authorized_dispatch`. Expiry uses the existing
MAX_TIME plus scheduler grace calculation. Re-registration of the same live
attempt preserves expiry and the Runtime's fallback dispatch timestamp.

Claim acquisition takes the fence mutex before inspecting authorization or its
version, and holds it through claim creation and token binding. For these
dispatches, successful `executor_claim.py acquire` returns exactly one
`claim_token=<opaque value>`. Only its SHA-256 is saved in the permanent claim.
The winning worker retains the token in its session; duplicate wakes never receive
it. Missing/lost tokens fail closed and cannot be regenerated by re-acquiring a
claim. Tokens supplement the live check; an old token is useless after retirement.
Treat the token as an attempt capability; do not put it in receipts or deliverables.

`scripts/executor_fence.py` provides:

- `check`: revalidate identity, project, claim/token, inbox hash, live
  WAITING_EXECUTOR state, expiry, STOP/HUMAN_REVIEW, and absence of completion.
- `prepare`: the same validation, then create the attempt's private candidate
  directory at `<project>/attempt_workspaces/<MESSAGE_ID>-<nonce digest>/`.
  It does not clone canonical files or grant canonical write permission.
- `publish`: snapshot one candidate, verify its SHA-256, recheck authority, then
  atomically replace the same project-relative canonical path. The Runtime records
  the identity/project/path/hash under `handoff/executor_publications/`.

Supported publish paths are files below `workspace/`, `evidence/`, and `reports/`.
`reports/USER_STATUS.md` is excluded. Files are limited to 64 MiB per publication.
Upward/absolute paths, Windows device aliases/alternate streams, symlinks,
junctions and hard-linked files are refused when observed by path validation.
The original `projects/<project-id>` path and its ancestry are checked for
symlinks/reparse points before resolution, including a junction at `projects/`
itself. This does not prevent concurrent hostile topology changes. No deletions or
arbitrary Runtime Core publication are supported. Project memory updates belong in the receipt for
Supervisor incorporation; the worker does not overwrite `RESEARCH_STATE.md`.

All commands use the five **original claimed** identity arguments, plus
`--claim-token "<token returned to this worker>"`. A worker never adopts the latest
inbox identity after a pause. Example command forms:

```text
python scripts/executor_fence.py prepare --message-id <id> --task-id <task> --stage-id <stage> --attempt <attempt> --nonce <nonce> --claim-token <token>
python scripts/executor_fence.py check --message-id <id> --task-id <task> --stage-id <stage> --attempt <attempt> --nonce <nonce> --claim-token <token>
python scripts/executor_fence.py publish --message-id <id> --task-id <task> --stage-id <stage> --attempt <attempt> --nonce <nonce> --claim-token <token> --path workspace/U1.txt --sha256 <candidate-sha256>
python scripts/executor_completion.py commit --staging-dir <staging-dir> --claim-token <token>
```

Use absolute helper paths if the shell's working directory is the candidate
directory. Check/prepare return `ATTEMPT_AUTHORIZED` / 0; publish returns
`PUBLICATION_COMMITTED` / 0. `ATTEMPT_FENCED` / 12 means stop, preserve candidates
and claims, and leave recovery to Runtime/Supervisor. Other nonzero errors also
fail closed. Check success is a snapshot, never permission for a later direct write.

Mandatory checkpoints: immediately after claim, on every resumed/continued session,
before each work batch or mutation-capable tool/command, before each publication,
and before completion. All work, scratch files and subprocess output go in the
returned candidate workspace. Read canonical inputs without modifying them; copy
needed inputs into the candidate directory. Pin all paths to the claimed attempt.

Completion staging remains in a fresh identity-specific directory under the
project's `completion_staging/`. For fenced attempts, every EVIDENCE/DELIVERABLES
manifest entry must match a Runtime publication record and the canonical file
hash observed during commit validation. This is not an immutable snapshot of
canonical files: direct mutation after that observation is not guaranteed to be
detected at commit or consume. The staging manifest hash and parsed receipt do
come from the same byte snapshot, even if staging is subsequently replaced.
The existing commit/consume/seal lifecycle and duplicate result codes remain.
Manifests are not an inventory of every filesystem effect; arbitrary receipt text
is still evidence for Supervisor review, not mechanically proven output provenance.

## Ordering and recovery

`control/.executor-fence.lock` is an OS-backed cross-process mutex used by
claim acquisition, checks, publication, dispatch registration, timeout retirement,
Supervisor entry retirement, completion commit, reconciliation and consumption.
It covers file IO and hashing; its duration depends on file sizes and storage
latency. Acquisition currently fails closed after 10 seconds of contention,
which can stop the Orchestrator and require restart. It is never held across an
Executor stage or model invocation. The kernel releases the lock on process death;
the persistent lock file is never deleted or treated as a permanent claim.

Timeout durably records the identity in `retired_message_ids` and an identity-bound
`executor_retirements` entry, with reason/time. It saves `pending_executor_timeout`
in the same Runtime state replacement, **before** invoking the Supervisor. A fresh
dispatch also retires its predecessor before releasing the mutex. Supervisor entry
retires the previous dispatch before allowing that model to change lifecycle state.
Restart replays a pending timeout event instead of reauthorizing the retired wait.
Missing or invalid `ISSUED_AT` uses the original Runtime dispatch timestamp;
restart of that identity preserves its registered expiry rather than renewing it.

If completion acquires the mutex first and commits, the timeout path sees the
ledger and does not retire it—even if compatibility artifact publication crashed.
A running Orchestrator repairs a missing DONE hint from the matching committed
ledger during polling and consumes it through the normal validation path, without
restart or manual repair. Repair/consume use the fence mutex so a live commit
cannot republish its final hint after consumption. Startup also reconciles ledger
bookkeeping and replays consumed work awaiting a Supervisor decision.
If retirement wins first, publication and completion are rejected. A publication
already linearized before retirement is legitimate output from the old attempt;
it does not count as completion and is not silently removed.

Publication is atomic **per file**, not across U1–U3 or a whole stage. A crash after
file replacement but before its publication record can leave an unreceipted file.
Completion cannot certify that file until a still-authorized owner republishes it.
After retirement it stays as partial prior output for Supervisor review. A crash
before completion creates no completion; normal ledger recovery covers crashes
after commit and between consume and Supervisor decision.

## Architecture limits and rollout

This is a mechanically enforced helper/publication protocol, **not an OS sandbox**.
ZCode remains an independently running process with filesystem access under the
same user. Runtime cannot intercept its arbitrary direct writes, rewrite a paused
session's cached instructions, kill all detached subprocesses, prevent hostile
mutation of control files, or fence remote services. Attempt directories provide
path separation, not ACL isolation. Path checks do not defend against a hostile
same-user process racing filesystem topology changes. A publisher paused while
holding the mutex blocks retirement/new dispatch; lock contention fails closed.

Before deploying this change: pause wakes, stop existing Executor sessions and
their child writers, safely stop the Orchestrator, update code and the installed
Scheduled Automation prompt together, and recover old attempts through reviewed
Runtime procedures using fresh identities. Do not resume old direct-write sessions.
Already-claimed legacy dispatches cannot be upgraded in flight by registration.
Existing legacy completion records remain readable; legacy helper completion
compatibility still rejects retired/timed-out identities. This patch changes new
dispatch execution requirements; it is not a transparent live upgrade.

A hard guarantee against bypass requires a restricted Executor account/container
or tool broker that denies canonical/control writes and exposes only the Runtime
publication capability. Runtime-controlled multi-file generation pointers would
be a separate design if stage-wide atomic publication becomes necessary.

## Regression evidence

`scripts/test_executor_fence.py` reproduces the incident with synthetic identities
700110 and 700111. It verifies stale resume rejection before writes, preservation
of U1–U3, fresh attempt publication, duplicate wake rejection, immutable claims,
deadline enforcement, both publication/retirement lock orderings, restart replay,
completion/timeout ordering, provenance/path checks, and kernel lock crash release.
Adversarial-review regressions additionally cover delayed startup with missing or
invalid `ISSUED_AT`, registration racing claim acquisition, live recovery without
DONE, commit/consume serialization, and staging replacement during validation.
Portable tests inject Windows reparse metadata and require rejection before
project path resolution. A separate Windows test creates actual directory junctions
at both `projects/` and `projects/<id>`; it skips on non-Windows systems or when
junction creation is unavailable. It does not cover every NTFS alias or a hostile
process changing topology during validation.
The broader suite covers existing consume/seal, Goal Anchor, Final Verification,
claim, isolation, startup and repair behavior.

Development-worktree verification: `python -m unittest discover -s scripts -p "test_*.py"`
completed successfully after adversarial-review fixes (325 tests, 3 skipped).
The focused fencing suite passed all 24 tests, including both native Windows
junction cases. The unmodified HEAD timeout path was
also reproduced in an isolated fixture: it saved the notification without retiring
700110. No production state was changed or deployment performed.
