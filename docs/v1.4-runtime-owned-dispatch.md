# v1.4 Phase 1 — Runtime-Owned Ordinary Dispatch

Implemented on the Phase 0 baseline in this development checkout. The Supervisor
now proposes ordinary work once; Runtime constructs its candidate wire and task
projections. **Construction does not authorize execution.** The existing control
revision, decision receipt, exact dispatch archive/seal and registration remain
authoritative.

This slice does not change Executor claim, fence, publication or completion code,
Scheduled Automation, Human Decision transactions, or Final Verification. Executor
Prompt V2 has not been started.

## Ownership boundary

| Responsibility | Before | After, ordinary dispatch |
| --- | --- | --- |
| Objective, logical task/stage, inputs/outputs, acceptance, task restrictions/stop conditions | Supervisor | Supervisor, in one semantic proposal |
| Time/retry intent | Supervisor-authored wire fields | Supervisor proposes bounded values; Runtime validates and applies limits |
| MESSAGE_ID, TASK_ID, STAGE_ID, ATTEMPT, NONCE, ISSUED_AT | Supervisor | Runtime |
| Wire/claim versions, model/review constants, scheduler grace | Supervisor copies constants | Runtime supplies constants |
| EXECUTOR_PROTOCOL and baseline restrictions | Supervisor reconstructs instruction strings | Runtime supplies the canonical v1 protocol and baseline restrictions |
| current_task, next_message_id, new decision's identity mirrors | Supervisor maintains matching copies | Runtime derives them from the prepared task |
| Decision/rationale, goal alignment, lifecycle choice, memory | Supervisor | Supervisor; existing decision history contract retained |
| Revision validation, decision receipt, archive, authorization | Runtime | Same Runtime boundaries |

The implementation is [ordinary_dispatch.py](../scripts/ordinary_dispatch.py),
called from the existing `_decision_transaction` in
[supervisor_control.py](../scripts/supervisor_control.py). `invoke_codex` marks new
non-Human-Decision turns as requiring semantic ordinary dispatch, and rereads state
after Runtime preparation. A full-wire ordinary result in those turns is rejected.
The compatibility entry point and already-durable pre-upgrade turns retain their
old wire handling; this does not bypass validation or authorize historical files.

## Model-visible before and after

Previously the Supervisor wrote `TO_ZCODE.md`, including five matching identity
fields, time/nonce/version/model values and 16 Executor protocol instruction
strings. It also wrote the matching `current_task`, advanced `next_message_id`, and
copied the new identity into its decision records.

Now it writes this field in the active `project_state.json`:

```json
{
  "ordinary_task_proposal": {
    "logical_task": "summary",
    "logical_stage": "check-evidence",
    "objective": "Produce a checked summary of the supplied evidence.",
    "inputs": ["evidence/source.txt"],
    "outputs": ["reports/summary.md"],
    "acceptance_criteria": ["Every finding cites supporting evidence."],
    "forbidden_actions": ["Do not modify the source evidence."],
    "stop_conditions": ["Stop if the supplied evidence is unreadable."],
    "max_time": 900,
    "max_retries": 2
  }
}
```

It records one ordinary semantic decision (`CONTINUE`, `REVISE`, `REDIRECT`, or
`CHANGE_METHOD`), including reason and goal alignment, in the existing latest and
history records and sets `WAITING_EXECUTOR`. It leaves `current_task` and
`next_message_id` unchanged and omits new decision identity fields. Runtime checks
these against its pre-invocation snapshot. The Supervisor also leaves the inbox
unchanged. Any leftover proposal must be removed when selecting terminal/FV work.

Required keys are `logical_task`, `logical_stage`, `objective`, `inputs`, `outputs`,
and `acceptance_criteria`. Text must be non-empty; the latter three fields are flat
string arrays, with non-empty outputs and acceptance criteria. Logical names are
trimmed, limited to 120 characters and contain no control characters. Arrays hold
at most 100 entries; individual substantive strings are limited to 16,000 characters.
Optional restrictions and stop conditions default to empty arrays. Unknown keys,
objects/nested arrays, physical identity, custom protocol, or FV metadata fail
validation rather than being silently dropped.

`max_time` accepts integer seconds 1–2700, default 2700, matching the existing
45-minute default timeout. `max_retries` accepts integers 0–2, default 2. Booleans
and strings are rejected. These are explicit limits of the new proposal API;
historical wires keep their existing deadline behavior. Runtime supplies 3600
seconds of scheduler grace. These limits do not change the automation cadence.

The prompt builder replaces only the legacy Task dispatch section inside the
existing 14,000-character delivered contract prefix with this proposal contract.
It updates ordinary stage/repair instructions. Other injected state, goal, profile,
memory and brief surfaces retain their prior selection/caps. The full-wire
[template](../control/EXECUTOR_TASK_TEMPLATE.md) remains a compatibility reference
for FV and Human Decision. The existing timestamp/nonce seed wrapper remains
available for those full-wire cases; an ordinary proposal never echoes it.

## Candidate construction, retries and recovery

Preparation runs under the existing Executor fence mutex, after the turn's
revision/pause check and the existing decision/history validation. It resolves the
active project and validates the semantic proposal before reserving an identity.

Runtime allocates a message ID at or above the snapshotted next counter and above
known archived, reserved, claimed, retired, dispatched and processed identities
across projects. Corrupt/incomplete history fails closed. Task/stage identifiers
derive from project-bound logical names; a cryptographically random nonce and
timezone-aware issue time are generated once. Semantic logical names are also
retained as `LOGICAL_TASK` / `LOGICAL_STAGE` in the wire and current-task view.

For the same project's same logical pair, previously authorized dispatches determine
the next attempt number. The effective retry limit is the minimum of the new intent
and earlier limits for that pair; a later proposal cannot increase it. Different
logical work starts at attempt 1. The Supervisor remains responsible for deciding
whether work is substantively different: Runtime cannot infer that from prose.
Authorized but unclaimed dispatches conservatively count toward this limit.
Retry grouping uses the new logical-name metadata; historical full-wire IDs are
not silently reinterpreted as logical names. The Supervisor must carry forward
any tighter historical task/method limit in its new bounded intent.

One create-only record under
`control/ordinary_dispatch_preparations/<supervisor-turn-id>.json` stores the exact
task, resulting state, state/task hashes and turn/project/revision bindings before
either projection is written. Runtime then replaces state and the candidate inbox.
It removes the proposal from live state, fills task/counter/decision projections,
and proceeds through the existing candidate validator and decision receipt.
Reservations are machine history, not an Executor inbox or authority record.

Crash recovery accepts only the bound pre/post state and expected pre/post inbox,
and reuses the same reservation. It generates identical bytes on first construction
and replay, including JSON ordering. Receipt reconstruction is read-only. Recovery
after a newer control revision cannot construct or authorize stale work. Abandoned
reservations permanently burn their message IDs; gaps are intentional. An invalid
proposal reserves nothing. A rejected prepared candidate burns its identity but
does not spend an authorized Executor attempt.

The existing decision retry and dispatch repair budgets also cover semantic
validation failures. Restart does not reset those budgets. Claimed retries retain
the old permanent claim and retirement history and receive fresh message IDs and
nonces. Reusing a reservation never reacquires a permanent claim.

## Safety and compatibility

After preparation and even after decision receipt creation, claim acquisition
still fails until `register_dispatched_task` validates the current exact candidate,
checks control origin/revision and seals the immutable dispatch archive. A revision
change between preparation and registration rejects the candidate. Existing startup
registration, expiry, retirement, claim ownership, completion and Goal Anchor checks
remain in force. No new authorization shortcut or claim/fence/completion protocol
was introduced.

The canonical generated protocol is copied verbatim from the v1.3 template. It
retains acquire/prepare/check/publish/commit instructions, failure exits, token
handling, path limits and the prohibition on direct canonical writes. Executor
input still contains this protocol. The helpers remain a cooperative same-user
filesystem boundary, not an OS sandbox. This slice does not resolve the Phase 0
invalid-staging prose contradiction or change any Executor exit behavior.

No historical identity, archive or receipt is migrated. Human Decision still uses
its read-only structured full-wire transaction. FV keeps its existing semantic
request/gate preparation and terminal acceptance checks. Ordinary proposals reject
FV fields and decisions. The new Runtime reservations add durable storage and a
history scan; their performance has not been benchmarked. Preserve these records
along with existing Runtime history across restart/upgrade.

Comparison uses the saved [Phase 0 census](../evidence/v1.4-intelligence-overhead-audit/context-census.json)
and the same offline builder probes. Reproduce with:


Results and complete task-equivalent output fixtures are recorded in
[context-comparison.json](../evidence/v1.4-runtime-owned-dispatch/context-comparison.json).
Counts are decoded UTF-8 text with LF normalization and the same synthetic root,
time and nonce normalization used in Phase 0.

| Surface | Before characters | After characters | Reduction |
| --- | ---: | ---: | ---: |
| Synthetic GENERAL bootstrap prompt | 22,527 | 19,183 | 3,344 (14.84%) |
| Synthetic result prompt | 22,621 | 19,277 | 3,344 (14.78%) |

| Delivered Runtime contract section | 14,049 | 10,687 | 3,362 |

The output comparison compactly serializes the old task wire, minimum required
current-task projection, next counter and one decision identity projection, versus
the new proposal. Both fixtures describe the same checked summary, files, criteria,
restrictions, stop conditions and bounded intent. Unchanged decision rationale,
history/memory and lifecycle text are excluded. It is a reproducible **synthetic
authoring-surface comparison**, not an observed model response or production average.

There were no live Supervisor/Executor calls or measured provider token/latency
savings. Host prompts, tool schemas/output, hidden history and later turns are not
included. No character-to-token conversion is made. No Executor context reduction
is claimed. The Phase 0 state/history truncation finding remains; its large-history
probe still omits the latest sentinel. No full context redesign is included here.

## Validation

Focused tests in [test_ordinary_dispatch.py](../scripts/test_ordinary_dispatch.py)
exercise ordinary semantic success through production invocation, strict invalid
proposals/projections, absent authorization before registration, stale revisions
on both sides of preparation, every preparation/receipt crash boundary, altered
state recovery, claimed retry limits, permanent claim retention, reservation gaps,
cross-project uniqueness, pause before physical preparation, Human Decision
compatibility and restart-persistent Supervisor retry exhaustion.

The full repository run completed **1,367 tests in 407.456 seconds, with 3 skips**
(no active project pointer in this clean checkout). The final Runtime-specific
regression completed **373 tests in 70.574 seconds, with no skips**, including all
17 new tests and the final pause/compatibility fixes. Commands, run ordering and
non-failing console cleanup warnings are recorded in
[validation.txt](../evidence/v1.4-runtime-owned-dispatch/validation.txt).

## Remaining Protocol → Runtime migrations

The following Phase 0 recommendations remain outside this slice:

1. Executor entry adapter for acquire/prepare and attempt-bound task/capability views.
2. Runtime publication/completion packaging of hashes, manifests and receipt identity.
3. Role/event-specific context budgets and removal of broader protocol duplication.
4. Bounded state/history/receipt views that preserve recent decisions and criteria.
5. Semantic decision/lifecycle/acceptance projection beyond the dispatch identity mirrors.
6. Host-owned wake/launch gating and trusted Executor latency/usage telemetry.

Future work can also consider semantic task proposals inside the unchanged Human
Decision and FV authoring paths. Existing Goal Anchor, authorization/archive,
claims/fencing, completion ledger and FV metadata/envelope migrations are preserved.
Phase 1 stops here; Executor Prompt V2 is not part of this change.
