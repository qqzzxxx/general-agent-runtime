# v1.4 Phase 5 — Capability Realization

Implemented in the development checkout on top of completed Phases 0–4. Phase 5
adds **bounded HTTPS retrieval and real static HTML rendering** to V2. HIGH can now
inspect rendered layout at multiple viewport sizes, revise a candidate, inspect
again, and publish the result and screenshot evidence through existing completion.
Capability descriptions explicitly separate Runtime enforcement, trusted host
observations, cooperative/unverified host tools, and unavailable operations.

This is a deliberately bounded capability expansion. Arbitrary shell commands,
builds, executable tests, JavaScript application interaction, general browsing and
desktop automation remain unavailable for V2 task work. ZCode has relevant host
tools, but their installation is not Runtime authorization or proof of safe
mediation. No OS sandbox, live ZCode integration test or model-quality improvement
is claimed. **Stop point: Phase 5.** No live automation was installed or changed.

The current official documentation supports the distinction. ZCode's browser is
provided by a plugin and depends on session configuration; it supports its own
tabs, navigation, forms and screenshots. The Runtime does not inherit that host
session merely because it runs a Python helper.
[ZCode Browser Automation](https://zcode.z.ai/en/docs/browser-use).

ZCode describes MCP as an additional tool source and documents a configurable
Windows shell. Those are host capabilities, not this Runtime's sealed grants.
[ZCode MCP](https://zcode.z.ai/en/docs/mcp-services),
[ZCode installation and shell settings](https://zcode.z.ai/en/docs/install).

Hooks can deny or alter tool calls, but current documentation says project hooks
are ignored; user hooks require enablement and plugin hooks depend on installation.
There is no verified, fail-closed, attempt-bound hook deployment here. A future
trusted host integration would need coverage, session binding, revocation and
failure behavior validated before changing its assurance classification.
[ZCode Hooks](https://zcode.z.ai/en/docs/hooks).

Scheduled tasks have their own project, permission and model settings, and some
can deliver subsequent triggers into an existing session. The repository's
rendered prompt does not reveal those settings or session history.
[ZCode Automations](https://zcode.z.ai/en/docs/automations).

## Capability and assurance model

Each V2 capability has a mode, availability, operations and an `assurance` value.
The distinction is about **specific guarantees**, not whether every part of the
computer is trusted or whether the model's judgment is correct.

| Assurance | Meaning | Phase 5 realization |
| --- | --- | --- |
| `runtime_enforced` | Runtime checks the stated scope and operation constraints in its adapter. It does not intercept independent host tools. | Scoped filesystem operations; exact-URL HTTPS GET with destination, TLS and response controls. |
| `trusted_host` | Runtime gates and bounds the request, but relies on a host provider for the result and its controls. | A fresh local Chromium process supplies static rendered DOM, geometry and pixels. Runtime fences source/evidence IO; Chromium implements rendering and browser restrictions. |
| `cooperative_unverified` | A host surface may exist, but Runtime has no trusted task/session binding or sufficient mediation. | Installed ZCode shell, web, browser and GUI surfaces in the read-only inventory. They have `task_work_authorized: false`; prose or self-report cannot promote them. |
| `unavailable` | No permitted implementation exists for this task, or prerequisites cannot be supplied. | Unrequested modes; arbitrary shell and GUI; interactive browsing/application execution; absent render dependencies. |

`executor_capabilities.py` owns supported modes, descriptions, URL syntax and
read-only dependency/installation discovery. Its inventory is descriptive and
grants nothing. `executor_contract.py` validates sealed execution preferences and
projects the task; `executor_entry.py` checks requested render prerequisites before
acquisition. `executor_work.py` remains the sole V2 task-operation endpoint.

No arbitrary command runner, host-tool forwarding operation, plugin registration,
capability attestation supplied by the model, or trust override was introduced.
A command's working directory cannot enforce filesystem isolation, and a list of
allowed command names cannot confine code those commands load. Given the current
host integration, that would require accepting effects beyond existing V2 scope.
Shell remains command transport for Runtime helpers only.

## Sealed policy and defaults

The ordinary proposal's existing `execution` field, copied into sealed `EXECUTION`,
can now request:

```json
{
  "autonomy": "HIGH",
  "capabilities": {
    "filesystem": "workspace",
    "shell": "none",
    "network": "https_get",
    "browser": "render",
    "gui": "none"
  },
  "read_paths": ["inputs/product-brief.md", "workspace", "evidence"],
  "network_urls": ["https://example.com/"]
}
```

Defaults remain NORMAL, filesystem `workspace`, other categories `none`, and
project read paths `workspace`, `evidence`, `reports`. Autonomy never adds tools.
LOW/NORMAL/HIGH produce identical capabilities for identical policy.

`network_urls` accepts at most 20 unique, exact ASCII HTTPS URLs, at most 2048
characters each. Only port 443 is supported. Userinfo, fragments, controls and
ambiguous URL forms are rejected. Queries, when present, are part of the exact
sealed grant; they are not constructed from runtime secrets. `https_get` requires
a nonempty list; nonempty URLs with network `none` are invalid. `render` requires
filesystem `workspace` because it retains screenshot evidence. Full-wire tasks
can carry the same execution preferences. Unknown modes, keys and purported
guarantees fail closed.

There is no new dispatch wire version, authorization source, claim mechanism or
durable permission file. The existing exact-byte dispatch/archive binding seals
both task and policy. Changing the grant after claim invalidates entry. Missing
requested browser dependencies stop V2 before claim; a retained owner cannot
silently downgrade or switch to V1 when the provider disappears.

## Operations and verification limits

Send one JSON object on stdin to the unchanged transport:

```text
python "<RUNTIME_ROOT>/scripts/executor_work.py" --session "<retained session>"
```

The Phase 4 `list`, `read`, `write`, `copy` and semantic `finish` operations retain
their scope, limits and completion behavior.

### HTTPS retrieval

```json
{"op":"fetch","url":"https://example.com/"}
```

`executor_fetch.py` is a fixed private worker. It resolves the granted hostname
once, rejects empty or mixed public/private answers, multicast, reserved,
IPv4-mapped and known IPv6 translation/tunnel address ranges, then connects to a
validated numeric address. TLS checks the original hostname and certificate chain
using the default trusted roots. There is no second DNS lookup at connection time.
It adds no authorization/cookie headers, ignores proxy environment settings, follows
no redirects, accepts only 2xx responses and uncompressed UTF-8 bodies, and reads at
most 256 KiB. Nonconforming responses produce no successful observation.

The parent gives the worker a 15-second communication timeout, including DNS; socket
operations also have timeouts. Cleanup and fence acquisition can add wall time.
The result includes URL, HTTP status, content type, text and Runtime-computed body
SHA-256. The hash binds bytes, not remote truth. TLS is not proof that a page's
claims are correct. This capability performs retrieval, not search or authenticated
browsing. It trusts OS routing and the certificate store; it is not a host-wide
network firewall.

**GET is a method restriction, not proof of no remote side effects.** Servers can
mutate state on GET. A timeout or later revocation cannot recall an issued request;
the result remains unavailable rather than being recorded as success. There is no
automatic redirect, retry, credential discovery or transactional rollback.

### Static browser inspection

```json
{"op":"render","area":"work","path":"workspace/signup.html","width":375,"height":812,"screenshot":"evidence/mobile-v1.png"}
```

The operation accepts a permitted project/work UTF-8 HTML snapshot, at most 256 KiB,
and a viewport from 320–1920 by 320–1080 CSS pixels. The screenshot must use a new
`evidence/*.png` candidate path. Existing safe-path checks reject traversal,
symlinks/reparse points, hardlinks, Runtime authority inputs and out-of-scope paths.

`executor_render.mjs` starts an installed Chrome/Chromium/Edge with a fresh temporary
profile and a local ephemeral CDP endpoint; it does not attach to ZCode or user tabs.
No project path or session token is sent to the worker. A single synthetic document
request is fulfilled from the snapshot. Page scripts, frames, workers, forms,
external resources, downloads and subsequent network requests are disabled with
browser controls, request interception and a restrictive response-header CSP. Inline
CSS and data images/fonts are allowed. The worker uses fixed Runtime-authored DOM
inspection code; the task cannot submit JavaScript, selectors, navigation, browser
flags or an executable path. The Chrome sandbox is not disabled.

The result supplies rendered text (with explicit truncation), title, viewport/content
dimensions, horizontal overflow, controls with labels and rectangles, script/resource
element counts, and the PNG path and hash. Runtime adds the exact input hash. Limits
include 5000 DOM elements, 200 controls, 16000 text characters and an 8 MiB PNG; the
parent worker timeout is 30 seconds. Browser dependencies are detected from host
installation paths/PATH. File presence is a prerequisite check, not a startup health
attestation: an old Node, broken CDP implementation or launch failure returns
UNAVAILABLE on invocation. Tested here with Node 24.18.0 and installed Chrome.

Browser controls such as
[script disabling](https://chromedevtools.github.io/devtools-protocol/tot/Emulation/#method-setScriptExecutionDisabled),
[request interception](https://chromedevtools.github.io/devtools-protocol/tot/Fetch/#method-enable)
and [screenshot capture](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-captureScreenshot)
are provided by Chromium. Their use does not create a Runtime OS sandbox or prove
that every browser background process has no network or filesystem access. Temporary
profiles and fixed workers are host housekeeping outside task candidate publication.
There are no hard CPU/memory quotas or crash-proof host process supervision.

This is useful for static product layouts, responsive geometry, text and control
inspection. It does **not** verify JavaScript behavior, backend integration, loading
external assets, navigation, account creation or authenticated state. HTML containing
scripts may render its static content successfully; `script_elements` and the fixed
limitation identify the missing execution. That cannot satisfy a functional criterion.
The `visible` observation is a layout/display/visibility heuristic, not an occlusion,
viewport coverage, accessibility or contrast audit. Labels and geometry are facts for
the Executor to interpret, not acceptance judgments generated by Runtime.

The CLI returns JSON, not an image content block. Screenshot artifacts are available
for publication and reviewer inspection; **V2 does not deliver those pixels into the
Executor's vision input**. A path is not evidence that the Executor saw an image.
The permanent prompt states this. The development validation separately used image
inspection to review the screenshots; that is not a live ZCode vision test.

## Fencing, concurrency and completion

`executor_inspect.py` performs a two-phase observation:

1. Under the existing Runtime mutex, enter with the retained session, validate current
   policy and live authority, reject a started finish, validate scope, and snapshot input.
2. Release the mutex and invoke a fixed bounded worker. It receives only the requested
   URL or HTML/viewport and host browser path, never identity, claim token or project paths.
3. Reacquire the same mutex and re-enter. Validate authority, unchanged policy and absence
   of a started finish. For render, reread the scoped source and require byte equality.
4. Only then return the observation and atomically retain a screenshot in candidate space,
   using the existing final authority recheck immediately before replacement.

Interruption/retirement is not blocked by external IO. An in-flight observation may
drain until its timeout after revocation; its output cannot be returned or retained.
Even a worker error is re-fenced, so revoked owners receive STOP rather than an
UNAVAILABLE/CONTINUE recovery path. Source changes discard the stale render and allow
a fresh permitted inspection. A safely paused running owner can still finish, as before.
Unregistered, duplicate, wrong-token, expired, retired, superseded, interrupted,
finished and sealed attempts retain the existing entry/operation protections.

There is no automatic privilege expansion. Invalid requests and capability/path
violations stop. A permitted observation that cannot be obtained returns UNAVAILABLE
with no successful payload. The Executor must preserve missing checks in its result.
Network failure can follow a transmitted request; UNAVAILABLE no longer implies that
nothing happened outside Runtime. All successful output remains untrusted task evidence
for semantic acceptance, with browser output specifically dependent on the host provider.

Screenshot names are unused when created, but ordinary candidate files remain mutable
through existing operations. Returned hashes bind the observed version. Completion
provenance binds published bytes; it is not a new signed attestation of every claimed
inspection or protection against model-authored false findings or same-user bypass.
The Executor includes desired PNGs in the existing semantic result's artifact list;
Runtime publishes and constructs completion through Phase 3. No acceptance verdict,
next-stage authority, FV standard or completion lifecycle was changed. Unsupported
FV execution modes still fail V2, and negative FV judgments remain negative.

## Real quality-iteration workflow

[Measurement code](../scripts/measure_capability_realization.py) uses real sealed
dispatch, permanent claim, V2 entry, operations and publication in private temporary
Runtime roots. The fixture is a Fieldnotes sign-up **design prototype**, explicitly
unconnected to account creation. Criteria cover two viewport sizes (375×812 and
1280×900), horizontal overflow, associated labels, a descriptive action, controls
at least 44 pixels high, and the visible prototype disclosure.

The draft already passes the Phase 4-style source checks for a label and descriptive
button. Its fixed-width card breaks mobile layout and its controls are only 32 pixels
high. The source-only control reports PARTIAL with unverified rendered criteria. The
render-enabled HIGH workflow observes the defect, applies one scripted responsive CSS
revision with 48-pixel controls, and reinspects both viewports before finish.

| Filesystem source control | 2/2 | Unavailable to this policy | PARTIAL |
| First render revision | 2/2 | Mobile overflow; undersized controls at both viewports | Revise |

The canonical published page and all four screenshots have intact completion
provenance. The saved

[published prototype](../evidence/v1.4-capability-realization/render-iteration/workspace/signup.html),

## Validation and delivery boundary

The focused capability suite covers assurance/autonomy independence, strict modes and
URLs, missing providers before claim, default denial, exact URL grants, output size and
secret handling, private/mixed/mapped/translated DNS destinations, pinned connection/TLS
hostname, redirects/compression/non-UTF-8, timeout and malformed provider output,
safe pause, interruption during worker IO, source changes, finish freeze, retirement,
render path/viewport checks, and discarded screenshots after revocation. Real browser
tests detect/revise mobile overflow, publish evidence, suppress page scripts, block
file frames and make zero requests to an instrumented local HTTP canary. Ordinary
dispatch tests prove the new URL grant is sealed and rejects post-claim expansion.

The full repository suite passed **1,460 tests in 448.183 seconds, with 3 existing
clean-checkout skips**. The final focused capability suite passed **19 tests in
14.920 seconds**, including the last cleanup-path guard and real browser cases.
The ordinary dispatch suite passed all **19 tests**. Non-failing file/socket/process
cleanup ResourceWarnings from broader repository tests remain in the captured log;
the final capability suite emitted none. Run ordering and final commands are recorded in
[validation.txt](../evidence/v1.4-capability-realization/validation.txt), with detailed
output in [full-regression.txt](../evidence/v1.4-capability-realization/full-regression.txt).

Code and the regenerated permanent prompt must be deployed together through existing
setup renderers when a deployment is authorized. No new scheduler, model provider,
host session bridge, hook installation, lifecycle, context-budget system, live project
migration or release was included. Existing V1 clients and Phase 3 completion APIs
remain available; V2 never uses them as a fallback for unsupported capabilities.

**Phase 5 ends here.**
