# v1.4 Phase 6 — Host-Native Executor

Phase 6 changes V2 from an exclusive Runtime tool client into an outcome-owning
agent contract. The Executor may use the model and available shell, browser,
vision, web/network, GUI/CUA and other tools in its ZCode session. Runtime
authorizes the task and retains identity, task authority, lifecycle, stale-worker
checks, publication, completion, control/history, provenance and Final Verification
state. HIGH encourages exploration, inspection and useful iteration within that
task. Lack of host interception is described honestly instead of prohibiting tools.

Implemented in the development checkout on top of completed Phases 0–5, preserving
their existing changes and historical evidence. The starting documents were the
[Phase 0 audit](v1.4-intelligence-overhead-audit.md),
[dispatch](v1.4-runtime-owned-dispatch.md), [entry](v1.4-executor-entry-adapter.md),
[completion](v1.4-runtime-owned-completion.md), [V2](v1.4-executor-contract-v2.md),
[capability realization](v1.4-capability-realization.md), change policy, handbook,
architecture and fencing contracts. The restrictions in the historical Phase 4/5
reports describe those phases, not the current native-tool contract.

**No live ZCode model run or model-quality improvement is claimed.** The UI evidence
below is a scripted, real native-browser run through an isolated Runtime lifecycle.
No automation, provider, scheduler, production project, deployment or later phase
was changed. **Stop point: Phase 6.**

## Contract and implementation

The [permanent instructions](../control/ZCODE_SCHEDULED_AUTOMATION_PROMPT.md) now
lead with outcome and method ownership. They remove the helper-only shell rule,
the ban on direct host tools/arbitrary Python, and the prohibition on viewing
screenshots with host vision. They distinguish a recoverable native-tool failure
from a Runtime STOP. They retain task restrictions, honest evidence, session
ownership, one-task scope, canonical publication and semantic completion.

| Executor-visible subject | Phase 5 | Phase 6 |
| --- | --- | --- |
| Method | Advertised Runtime operations only | Choose effective methods using available session tools |
| Native shell/browser/web/GUI | Not granted because not Runtime-bound | Permitted by default for the authorized outcome; availability remains session-dependent |
| Vision and other tools | Missing capabilities could not be replaced by host tools | Use them when present, subject to explicit restrictions |
| HIGH | Iterate within bounded adapter operations | Explore, inspect, compare useful alternatives and iterate using the available environment |
| Enforcement description | Cooperative/unverified host status implied prohibition | `cooperative_unverified` describes lack of interception/attestation, independently of permission |
| Filesystem/fetch/render | Exclusive execution path | Optional deterministic utilities with their existing operation limits |
| Native locations | Hidden from V2 | Validated read-only project-input root and attempt work root |
| Live checks | Implicit in every mediated operation | Same checks, plus session-only `checkpoint` before native batches and entry on resume |
| Missing render dependency | Denied the whole entry, including unrelated operations | Entry remains valid; an attempted render reports UNAVAILABLE |
| Publication/completion | Semantic finish through existing fence/ledger | Same authority path, including native-produced files |
| Final Verification | Fixed claims/results, LIVE_READ_ONLY | Same fixed judgments; explicit host inspection without modifying verified deliverables; new evidence namespace |

The changes are concentrated in:

- [`executor_contract.py`](../scripts/executor_contract.py) and
  [`executor_capabilities.py`](../scripts/executor_capabilities.py): native defaults,
  restrictions and separate optional utility descriptions.
- [`executor_entry.py`](../scripts/executor_entry.py): exposes locations only after
  the existing authority/claim checks. `locations.candidate_work_open` reports a
  frozen finish; neither the path nor a READY snapshot is a lasting write grant.
- [`executor_work.py`](../scripts/executor_work.py): adds `{"op":"checkpoint"}`.
  It uses the existing entry/fence mutex and token checks and refuses frozen work.
  No command runner, host forwarding, task-creation or authorization operation exists.
- [`executor_inspect.py`](../scripts/executor_inspect.py): consults utility policy.
  Source snapshots, exact URL checks, response limits and post-IO fencing remain.
- [`executor_fence.py`](../scripts/executor_fence.py) and
  [`executor_finish.py`](../scripts/executor_finish.py): enforce explicit filesystem
  publication restrictions at the lower publication boundary, and prevent FV
  publication from replacing verified deliverables or existing evidence.
- [`ordinary_dispatch.py`](../scripts/ordinary_dispatch.py): the Supervisor authors
  outcomes and genuine task restrictions; missing host mediation is not a reason
  to deny tool use. The exact dispatch/archive seal still binds execution policy.

V2 remains version 2; wire, authorization, permanent claim, ledger, provenance and
FV envelope schemas are unchanged. V1 entry and existing completion/replay APIs
remain available for compatibility. No host registry, self-attestation, new durable
credential, role-authentication system or automatic tool-installation path is added.

## Defaults and explicit restrictions

A new ordinary task can simply use `"execution":{"autonomy":"HIGH"}`. The
normalized defaults are filesystem `workspace`, shell/network/browser/gui/vision/
other `host`, and project `read_paths` of `workspace`, `evidence`, `reports`.
`other` covers remaining host tool categories; web tools are subject to network
policy. The Executor's model remains supplied by its host. LOW/NORMAL/HIGH have
identical permissions for identical policy.

| Mode | Meaning |
| --- | --- |
| `host` | Use available session tools for this category; `available: "session_dependent"`, `assurance: "cooperative_unverified"`, `task_work_authorized: true` |
| `none` | Explicit category restriction, including effects routed through other tools |
| Filesystem `read` / `none` | Respect declared read-only/no-task-file-access scope across tools; no artifact publication |
| Filesystem `workspace` | Candidate work in the attempt workspace; canonical inputs remain read-only |
| Network `https_get` | Preserve the legacy exact-URL, bounded Runtime fetch-only restriction |
| Browser `render` | Preserve the legacy static Runtime render-only restriction |

Unknown modes/keys still fail validation. Explicit `FORBIDDEN_ACTIONS`, stop
conditions, read paths, URL limits and bounded legacy modes survive projection.
An explicit sealed `none` is preserved even if a prior Supervisor originally
selected it because Phase 5 lacked support. Phase 6 does not guess its intention
or edit an existing authorization. A fresh task can select `host` when appropriate.

Optional `network_urls` is accepted with `host` or `https_get`; when supplied it
still bounds the task's URLs across tools. The fetch utility always requires exact
listed HTTPS URLs. Without that list, native network work is permitted by `host`
but Runtime fetch remains disabled. Native browser mode makes static rendering
available as an optional utility when filesystem mode permits evidence writes.
Absent Node/Chromium does not revoke the task; the utility reports its limitation
when called. An explicit `none` never becomes enabled by a missing dependency.

The filesystem utility keeps its 256 KiB text, 64 MiB copy/publication and scoped
path limits. Host tools are not subject to the adapter's text serialization limit;
publication still validates candidate path, size, hash and provenance. Paths shown
by entry do not authorize reading control/history or writing canonical files.
Normal host dependency access is allowed; another Runtime/project is out of scope.

## Authority and stale-worker boundary

Only READY/exit 0 supplies a task and the owner's retained session. Entry still
validates the exact live authorization, dispatch bytes/archive/seal, current
project, lifecycle, expiry, permanent claim and token. Resume never acquires or
adopts a successor. Duplicate/no-work/failure responses contain no task credentials.

Before native batches, checkpoint rechecks the same authority. On resume, entry
revalidates it. These checks do not mechanically gate every subsequent native
effect. A revoked same-user process can still write stale scratch; it cannot
publish or complete through the supported Runtime APIs. The owner must stop its
background writers before finish/exit. Runtime cannot automatically terminate
native browser/process activity or undo external effects.

Native files and tool results are candidate evidence, never task authority.
Control/history/ledger paths remain excluded from utility reads and publication.
The contract forbids editing Runtime files or invoking Supervisor/control APIs
to create or authorize tasks. The Executor endpoint has no such operations.
Completion still freezes the semantic result, snapshots/hashes selected artifacts,
publishes under the live fence and commits the existing ledger. All finish results
end the run. Reported recommendations and outcomes cannot select the next task,
change FV state or confer Final Acceptance.

**Protection scope:** these are supported-protocol and cooperative host boundaries,
not an OS security boundary. An unrestricted hostile same-user process can directly
edit files or invoke operator APIs, which do not gain new process-role authentication
in Phase 6. Tests do not prove prevention of those hostile actions. The accurate
claim is that native tool use itself conveys no additional Runtime authority and
cannot manufacture a valid task/completion through the Executor contract. This
limitation does not become a blanket prohibition on legitimate native tools.

## Final Verification

Supported V2 FV remains `LIVE_READ_ONLY`, preserving fixed claims, policy standards,
negative/unverifiable judgments and Runtime-owned pending/acceptance state. Browser,
vision, shell and other host tools may inspect them. They must not repair verified
deliverables or mutate live state. Mutation-capable checks require disposable copies
and permission from the bound FV policy; otherwise the Executor reports the gap.

Entry provides attempt-specific FV publication roots:

```text
evidence/verification/<attempt-directory>/
reports/verification/<attempt-directory>/
```

The underlying publication helper enforces those roots for LIVE_READ_ONLY FV,
including direct compatibility calls. It rejects workspace deliverable publication
and replacement of any existing canonical file. Atomic create prevents a file
appearing during IO from being overwritten. Finish preflights the whole package;
replay may verify its own already-recorded evidence without replacing it.

Publication remains per-file, not a transaction across files. A crash after FV
evidence creation but before its publication record leaves an occupied path that
fails closed on retry; Phase 6 does not infer provenance or replace it to recover.
Direct hostile native mutation remains outside interception, as described above.
Unsupported FV execution modes still fail rather than claiming an OS sandbox.

## Native UI demonstration

Reproduce with installed Node and Chromium:

```powershell
python scripts/measure_host_native_executor.py
```

The [measurement script](../scripts/measure_host_native_executor.py) creates a private
synthetic Runtime using real dispatch/archive/claim/entry code. It asks for a responsive
local sign-up demo with explicit criteria and no real account/data transmission.
After a session-only checkpoint, an independent Python process writes the candidate.
The [native browser probe](../scripts/host_native_ui_probe.mjs) launches Chromium from
the shell, opens that local file, executes its page JavaScript, sends native CDP
input/click events and writes viewport PNGs. It does not call Runtime write/render
operations or the restricted static renderer. Browser profiles stay inside the
attempt workspace and the probe closes its browser before finish.

| Fixed scripted check | Initial mobile | Initial desktop | Revised mobile/desktop |
| --- | --- | --- | --- |
| No horizontal overflow | Fail (881 CSS px content in 375 px viewport) | Pass | Pass |
| Associated email label | Pass | Pass | Pass |
| Descriptive submit action | Pass | Pass | Pass |
| Controls at least 44 CSS px high | Fail | Fail | Pass |
| Native input/click invokes local submit handler | Pass | Pass | Pass |
| Page JavaScript executed | Pass | Pass | Pass |

The viewports are 375×812 and 1280×900. The actual browser reports Chrome
153.0.8010.36 and Node v24.18.0. Source disclosure states that this is a local demo;
no backend or live service is tested. The revision and checks are scripted, not
model judgments. Screenshot capture makes native visual inspection possible; the
scripted Executor does not claim to have perceived the screenshots.

Review [browser observations](../evidence/v1.4-host-native-executor/ui/evidence/native-browser-observations.json),

## Executor-visible before/after measurement

The [captured measurement](../evidence/v1.4-host-native-executor/measurement.json)
records source hashes, complete projections, operation timings and limitations.
Before uses the saved Phase 5
[permanent prompt](../evidence/v1.4-host-native-executor/phase5-executor-prompt.md),

an actual READY response, paired with the saved
[Phase 6 permanent prompt](../evidence/v1.4-host-native-executor/phase6-executor-prompt.md).
Both use the same task. Only the session and absolute
locations are replaced with placeholders. Compare
[before entry](../evidence/v1.4-host-native-executor/before-entry.json) and

| Normalized Unicode character surface | Phase 5 | Phase 6 | Change |
| --- | ---: | ---: | ---: |
| Permanent template | 6,916 | 5,597 | −1,319 (19.07%) |
| Bound permanent prompt | 6,940 | 5,621 | −1,319 |

The permanent instructions are simpler, but the complete surface grows because
native permission/assurance, locations, restrictions and utility descriptions are
now explicit. No total context-saving claim is made. These are BOM-stripped,
LF-normalized characters and compact JSON, not provider tokens. Host/system prompts,
tool schemas, session history, model turns and provider latency remain unmeasured.
No live model comparison, quality improvement or character-to-token conversion is
reported.

## Validation and delivery

The focused [Phase 6 tests](../scripts/test_host_native_executor.py) exercise native
subprocess candidates, unchanged control/history before finish, exact-one completion,
protected paths and unsupported control operations, unregistered inboxes, stale
native writes, successor adoption rejection, safe pause versus interrupt, finish
freeze/resume, explicit read-only publication restrictions, optional dependency loss,
FV negative judgments, deliverable preservation and publication collision races.
Existing entry, claim, fence, completion/recovery, dispatch, lifecycle, provenance,
Goal Anchor, Human Review, Final Verification and setup-renderer regressions remain
part of the full suite.

The full repository regression passed **1,473 tests in 535.124 seconds, with 3
existing clean-checkout skips**. The focused Phase 6 suite passed **13 tests in
4.702 seconds**; capability (19), ordinary dispatch (19) and V2 contract (20) suites
also passed. The full run includes both setup renderers and all completion/lifecycle
regressions. Existing non-failing socket/process/file ResourceWarnings remain in
the broader test output; no new warning suppression was introduced.

The initial regression exposed two stale expectations about renderer dependency
loss and an internal helper name in the prompt. They were updated for the new
contract. A subsequent review correction ensures that an unconfigured optional
utility never describes native use as forbidden; the final full run includes it.
Final commands and test totals are recorded in
[validation.txt](../evidence/v1.4-host-native-executor/validation.txt) and the
[full regression log](../evidence/v1.4-host-native-executor/full-regression.txt).

Code and the regenerated automation prompt must be deployed together through the
existing setup renderers when deployment is authorized. This implementation and
evidence stop at Phase 6; no live deployment or later-phase work was performed.
