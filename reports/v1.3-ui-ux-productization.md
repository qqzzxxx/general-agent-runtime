# v1.3 UI/UX productization — bounded dogfood repair

Date: 2026-09-13 (Asia/Shanghai).

This pass follows the narrowing addendum. It repairs navigation, first-use discovery, desktop layout, normal Chinese product copy, and separation of settings. It does not attempt a comprehensive redesign of Timeline, task details, artifacts, or the four-step project workflow.

## Why rc1 failed human dogfood

- Independent feature panels accumulated inside one long document. There was no primary navigation or boundary between operations, setup, and preferences.
- Runtime creation followed all those panels. The no-Runtime state explained implementation history rather than providing a next action.
- The three-column layout reserved only 250/300 px for side panels. Definition lists used `max-content 1fr`: long labels could consume nearly all available width. `overflow-wrap: anywhere` then broke timestamps and paths into single-character columns.
- Later settings and creation controls lacked the component-specific styles applied to older panels. Inline labels and native controls had inconsistent sizing.
- Development prose, internal stage names, and English-only labels dominated the normal view. Static tests checked feature markers and security invariants, but not actual viewport geometry.

## Implemented boundary

Product source changes are confined to `web_console/index.html`; it remains the existing dependency-free HTML/CSS/JavaScript application. No backend Python, API contract, Runtime control implementation, authorization, claim/fence, completion, Registry isolation, HUMAN_REVIEW, or Final Verification code was changed. No push, merge, tag, or release was performed.

The new registration form uses the already-existing `POST /api/runtimes` with exactly `{root, label}`. Creation still uses `POST /api/runtimes/create`. Existing control handlers, confirmation flows, same-origin requests, notification permission gesture, setup steps, provenance checks, and inert previews are retained.

## Information architecture and visual system

- Fixed desktop sidebar: 项目控制台、时间线、产物中心、项目设置、设置; Create/Register appear above the scrollable Runtime list. Selection is highlighted, with a full-name tooltip for truncated labels.
- Only the selected major surface is displayed. Create and Register have their own surfaces. Hash navigation supports direct links; the selected Runtime and language preference survive reloads when local storage is available.
- The no-Runtime state offers 创建第一个 Runtime and 注册已有 Runtime, followed by a concise explanation of the setup sequence.
- The top bar shows the selected Runtime, reported project, current state/attention badge, and language switch.
- Cockpit prioritizes current worker, next action and human attention. Health uses stable label/value columns; exact timestamps and supporting identity facts remain in tooltips/details. Missing timestamps are still missing, and ZCode activity is not assigned an invented time.
- Settings and Supervisor configuration are reachable in Settings. Alert thresholds are collapsed under 高级. Long implementation notes remain accessible through disclosure.
- Shared typography, spacing, form controls, focus rings, disabled states, status badges, and primary/secondary/destructive treatments apply to existing panels. The two-column Cockpit collapses below 1190 px rather than compressing a third column. Small-screen rules remain a fallback; this is a desktop-first pass.

## Localization

Simplified Chinese is the default normal UI; English is selectable in the top bar. Navigation, creation/registration, empty states, common execution/health states, settings labels, setup controls, milestones, and routine/destructive action labels have Chinese copy. Option values and protocol identifiers are unchanged. Long technical documentation and unrecognized backend diagnostic messages may remain English in details. Raw artifact contents, dispatch bytes, paths and user-authored labels are not translated.

The language selector reloads the page. Save unsaved form edits before switching language. Deep-detail localization remains future work rather than part of a full product rewrite.

## Remaining limitations and operational notes

- This is the narrowed repair pass. Full detail-view localization, richer artifact layouts and a broader component rewrite were deliberately deferred.
- Real visual QA did not perform an Agent start, Formal STOP, or real external ZCode automation. Existing fixture/backend regressions exercise those contracts. Browser registration only targeted disposable fixture data.
- The existing lifecycle test suite calls `kill_stray_console_servers(REPO)` and cleans `web_console_data/instance.json`. It stopped the pre-existing **development Web Console backend** for this checkout; it did not stop the parent Builder Runtime. The tracked instance file is restored to the original repository content after the suite. That recorded PID is stale; restart the development Console with its normal launcher before using it again. The launcher verifies stale metadata. No Runtime operational state was restored or altered by the UI implementation.
- Initial visual-harness registration attempts timed out only while the Windows fixture process was waiting on an inherited stdin pipe. Switching the harness to a fixture-local signal file resolved this; the product backend was not changed. Initial diagnostics are retained as `initial-fixture-error.json` and `initial-fixture-error.png`. The final browser run passed.
- Automatic approval review blocked a bulk recursive cleanup of disposable browser profiles (`blocked by policy`, no further reason supplied). Earlier profiles remain under ignored `.test-tmp/ui-browser-*`; they are not product changes. The fixture Runtime trees and browser processes from completed runs are closed by the harness.

Stop boundary reached: representative rendering is acceptable, the complete rerun is green, and the diff check passes. No additional cosmetic redesign is undertaken.
