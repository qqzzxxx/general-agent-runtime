# Fresh Runtime first-project readiness repair

Scope: the Console-created fresh Runtime → Setup → readiness → formal project bootstrap path. No UI redesign, API schema change, or Runtime control semantic change.

## Reproduction and root cause

The regression fixture uses the real `POST /api/runtimes/create` endpoint, the supported release copier, real registry status validation, all four Setup draft/acknowledgement endpoints, and the real `GET /setup/readiness` endpoint. Neither status nor preflight is stubbed. Before the fix this produced exactly nine PASS checks and one FAIL: legacy preflight reported missing `control/project_state.json`, `RESEARCH_STATE.md`, and `ZCODE_LAST_PROCESSED.txt`, plus the resulting project-state load error. See [before-fix output](../evidence/fresh-runtime-readiness/before-fix.txt).

At the current checkout (`d337f1e` plus the preceding UI pass), there was no `interpret_fresh_install_preflight` implementation or equivalent in the production Setup path. `_compute_readiness` used `_run_setup_preflight` directly. Runtime creation correctly copies only the release skeleton and excludes all project lifecycle state. With no active project pointer, unchanged preflight enters legacy mode, which requires the three files above.

The old Setup HTTP fixture calls `arm_terminal_project` before testing readiness. Its existing COMPLETE project allows isolated-mode preflight to pass. The clean-release startup test also bootstraps before checking preflight. Neither exercises create → first-project readiness, so those passing tests did not cover this failure.

## Exact implementation changes

- `scripts/web_console_server.py`: apply the fresh-install interpreter in `_compute_readiness`, shared by GET readiness and POST start. The start route still recomputes readiness before calling the real bootstrap helper.
- `scripts/web_console_fresh_install.py` (new): read-only proof of eligibility for first-project bootstrap, limited to the supported empty release.
- `scripts/test_web_console_fresh_readiness.py` (new): production-path and refusal regressions.
- This report and `evidence/fresh-runtime-readiness/`: reproduction, validation and full regression records.

No changes to `preflight.py`, `start_project.py`, `START_PROJECT.ps1`, `orchestrator.py`, authorization, claims/fences, completion, STOP, HUMAN_REVIEW, or UI code in this repair. Earlier UI changes remain in the working tree.

## Why failure remains closed

The interpreter changes a failed result only when all these facts agree:

1. The real preflight exits with code 1 and its complete output is exactly the supported legacy missing-first-project failure. Extra errors, truncation, unknown output, launch failures and timeouts remain failures.
2. The real status document explicitly reports no project, runtime execution, task, authorization, claim, completion, intervention, STOP, HUMAN_REVIEW or non-default pause state. Missing or contradictory facts do not count as evidence of freshness.
3. The Runtime root, `control/` and `handoff/` have exactly the creation skeleton's inventories. Existing project directories, even empty ones, logs, pointers, state files, flags, locks, ledgers, dispatches and unknown entries disqualify it. This does not infer freshness merely from a missing active pointer.
4. Runtime control/bootstrap code, release root files, static control seeds and the complete profiles/policies match the Console installation's supported release bytes by SHA-256. Missing or changed required files disqualify it. Reparse points, unreadable files and excessive inventories fail closed. Generated Python bytecode caches are excluded from the product-file comparison, but are still checked for reparse points.
5. Every existing Setup requirement still passes independently: Goal validation and Anchor eligibility, ProjectType, explicit input decision, Supervisor draft, Runtime/Python health and ZCode acknowledgement.

This is a structural proof of an unchanged, empty supported installation; it is not a recovery mechanism for customized or partially erased installations. Console-only code may be newer than the Runtime's Console copy, so an already-created pristine dogfood Runtime remains eligible without copying new files into it.

Readiness writes no lifecycle files. The real `start_project.py` creates the isolated project state and memory, hashes and binds its Goal Anchor, then publishes `ACTIVE_PROJECT.json`. The bootstrap regression verifies those actual outputs and then reruns unchanged preflight, which returns OK in isolated mode. No legacy placeholders are created. Only the final process-launch boundary is mocked in that regression to avoid launching real agents; bootstrap itself is not mocked.
