# General Agent Runtime v1.3 Product Specification

**Target release:** v1.3.0  
**Baseline:** General Agent Runtime v1.2.0  
**Baseline commit:** `667d3c4bf49eaa8f4f9f8ee410505f06d08631c9`  
**Baseline tag:** `v1.2.0`

## 1. Product vision

General Agent Runtime v1.3 turns the reliable but terminal-oriented v1.2 control plane into a **local visual Agent operations console**.

A normal user should be able to open one local website and complete the full project lifecycle without using PowerShell for routine operation:

> create project → configure Codex and ZCode → start → understand every Agent round → inspect artifacts → pause / steer / deep-review safely → handle HUMAN_REVIEW → reach COMPLETE.

v1.3 is **not** a web shell. It is a human-readable control and observability layer over the v1.2 Runtime.

## 2. Product principles

1. **Human-readable by default.** Show what is happening, who is working, why Codex chose the next step, what ZCode returned, and what happens next.
2. **Transparent, not black-box.** Every formal Codex → ZCode dispatch and authoritative ZCode → Codex completion remains inspectable.
3. **Reuse v1.2 authority.** Web UI must call bounded Runtime control-plane operations, not edit authoritative state files or invent a second control path.
4. **Structure before AI.** Status, history, files, token usage, alerts, search, previews, and state-machine explanations should not require new model calls.
5. **Context-linked, not context-dumped.** Human feedback binds to Project / MESSAGE_ID / Artifact and lets Codex retrieve additional context as needed.
6. **Local-first security.** v1.3.0 listens only on `127.0.0.1`; no public/LAN remote control, accounts, or arbitrary web shell.

## 3. Multi-Runtime model

One Web Console manages multiple **isolated Runtime Roots**.

Example sidebar:

- `● NSST Research — ZCode working · 700126`
- `⚠ PPT Courseware — HUMAN_REVIEW`
- `○ Paper Writing — PAUSED`
- `✓ Smoke Test — COMPLETE`

Each Runtime keeps its own project, state, history, artifacts, interventions, automation setup, and safety boundaries.

The Console maintains an explicit **Runtime Registry**. It must not scan the whole disk automatically.

Registry functions:

- add existing Runtime;
- remove from registry without deleting files;
- rename display label;
- create a new Runtime from a supported stable release;
- validate Runtime compatibility/version.

## 4. Main information architecture

v1.3.0 has three primary surfaces.

### 4.1 Project Cockpit

The main daily-use screen:

- Runtime sidebar;
- Current execution state;
- Live Timeline;
- Recent Artifacts;
- Human Control;
- Pending Controls;
- Runtime Health;
- alerts;
- token/time summary.

### 4.2 Artifact Center

Dedicated output inspection workspace:

- file tree/list/gallery;
- preview;
- search/filter;
- provenance;
- MESSAGE_ID linkage;
- verification state;
- artifact-triggered STEER / Deep Review.

### 4.3 Project Setup

Four-step guided setup:

1. Goal + Inputs
2. Codex configuration
3. ZCode Automation setup
4. Readiness / Preflight / Start

Task details, settings, intervention forms, Human Review details, and protocol details should normally use drawers/modals rather than many separate pages.

## 5. Project Setup Wizard

### Step 1 — Project Goal + Inputs

Explain that `PROJECT_GOAL.md` defines the **destination**, not Runtime routing internals.

A Goal should normally contain equivalent content for:

- Objective
- Background / Context
- Available Inputs
- Required Deliverables
- Constraints
- Quality Requirements
- Acceptance Criteria

A Goal should not prescribe:

- MESSAGE_ID values;
- NONCE;
- claim/fence/completion mechanics;
- exact Supervisor-turn count;
- exact Executor-task count;
- exact authorization sequence;
- retry internals.

Support drag/drop and file picker for `.md` Goal files.

#### Project Inputs

Allow users to register files/folders such as datasets, PDFs, images, source code, experiment outputs, etc. Build a readable input inventory.

#### Goal Workshop with ChatGPT

Provide a button such as **“Discuss Project Goal with ChatGPT”**.

The Console prepares an external-AI context pack containing:

- Runtime Goal Workshop Contract;
- selected ProjectType;
- Runtime version;
- input inventory;
- Goal-writing rules;
- supported publication roots (`workspace/`, `evidence/`, `reports/`).

The repository should contain a canonical document such as:

`docs/WEB_AI_GOAL_WORKSHOP.md`

It explains Human / Goal / Codex / ZCode / Runtime roles and how to write a compatible Goal.

The Console may open ChatGPT and provide a one-click-copy startup prompt. v1.3.0 does not need to implement a full embedded AI chat.

#### Goal Validator

Mechanically check where possible:

- Markdown is readable;
- Project ID / ProjectType valid;
- Acceptance Criteria exist;
- obvious unsupported publication roots are rejected/warned;
- obvious Runtime-internal routing requirements are warned;
- referenced inputs/outputs are sensible.

The smoke-test failure where `artifacts/` conflicted with EXECUTOR-FENCE-V1 should be caught before Runtime start.

### Step 2 — Codex Supervisor Configuration

Allow user to select:

- Supervisor model;
- reasoning effort;
- decision explanation mode.

Possible options may include GPT-5.6 / GPT-6 and Low / Medium / High / Extra High / Highest / Ultra, but the frontend should prefer capabilities reported by the actual provider/runtime rather than hard-code assumptions forever.

Default decision explanation mode: **Compact**.

Modes:

- Minimal — structural state only;
- Compact — short decision summary each Supervisor turn;
- Detailed on demand — extra explanation only when requested.

Compact summaries should normally be about 100–200 output tokens and be generated inside the existing Supervisor turn, not through a second automatic model call.

### Step 3 — ZCode Automation Setup

The Web Console does not choose the ZCode model in v1.3.0.

Show:

- exact Runtime Root / Workspace;
- canonical Automation Prompt;
- one-click copy;
- setup instructions.

Suggested guidance:

1. Open ZCode
2. Create Scheduled Automation
3. Set Workspace to the displayed Runtime Root
4. Paste prompt
5. Choose model in ZCode
6. Enable Automation

User confirms setup manually unless a supported ZCode API exists.

Do not pretend the Console knows Automation state if no supported source exists.

### Step 4 — Readiness / Preflight / Start

Show readiness checks:

- Goal loaded;
- Goal Anchor ready;
- inputs registered;
- ProjectType valid;
- Supervisor configured;
- Runtime healthy;
- Python/runtime requirements;
- v1.2 Control Plane available;
- ZCode setup acknowledged;
- preflight passes.

Then expose one primary action:

**Start Agent Collaboration**

The UI performs the documented bootstrap/start workflow through bounded backend operations and transitions naturally into the Project Cockpit.

## 6. Runtime model changes while running

Changing Codex model/reasoning must not kill an active Supervisor turn.

UI should show:

- Current turn: GPT-5.6 Sol · High
- Next turn: GPT-6 · Highest
- `Model change queued — applies next Supervisor turn`

The current turn completes normally; new settings take effect next turn.

## 7. Project Cockpit layout

Desktop-first three-column layout:

### Left
Runtime / Project list + New Project

### Center
Current execution + Live Timeline + Recent Artifacts

### Right
Human Control + Pending Controls + Runtime Health

Center content may scroll while controls remain easy to reach.

## 8. Current execution panel

The most prominent block. It must answer:

- Who is working?
- What are they doing?
- Since when?
- What happens next?
- Does the user need to act?

Human-readable states include:

- Codex thinking;
- waiting for ZCode;
- ZCode executing;
- completion committed;
- completion consumed/sealed;
- Supervisor processing result;
- Final Verification;
- Pause requested;
- Paused;
- HUMAN_REVIEW;
- Complete;
- Stopped;
- Error.

Do not invent percent-complete values for ZCode. Show real protocol milestones instead:

`Authorized → Claimed → Working → Published → Completion committed → Consumed/sealed`

### Next Expected

Use deterministic Runtime-state interpretation to show messages such as:

- Waiting for ZCode to claim MESSAGE 700126
- Codex will evaluate the completion next
- System will pause after current completion
- Human decision required
- Final Verification may lead to COMPLETE

No AI call should be needed for this.

## 9. Supervisor Turn Observability

Add a structured record such as:

`SUPERVISOR-TURN-OBSERVABILITY-V1`

Record at least:

- turn ID;
- Project ID;
- start/end timestamps;
- model;
- reasoning effort;
- token usage when available;
- decision type;
- compact `decision_summary`;
- context manifest;
- resulting MESSAGE_ID if any;
- related intervention IDs;
- related completion MESSAGE_ID;
- validation/error outcome.

### Context Manifest

Record what the Supervisor was actually provided or consulted when known:

- PROJECT_GOAL;
- project state;
- long-term memory;
- Project Profile;
- current completion;
- human interventions;
- historical dispatch/completion IDs consulted;
- evidence/artifact paths consulted.

This is observability metadata, **not private chain-of-thought**.

## 10. Decision Summary

Each normal Supervisor turn may generate a short human-readable reason, e.g.:

> Current results satisfy the primary task but have not been independently verified, so Final Verification is required before completion.

Default target: about 100–200 tokens maximum.

Deep explanation may be requested later and can consume additional model usage.

## 11. Timeline

Timeline is the central project history.

### Round structure

A logical round may group:

1. Codex Decision
2. Codex → ZCode Dispatch
3. ZCode → Codex Completion

Human interventions, audits, warnings, HUMAN_REVIEW, errors, and completion events appear where they occurred.

### Collapsed view

Show:

- Round / MESSAGE_ID;
- status;
- duration;
- task summary;
- short result;
- token usage where available.

Example:

`700126 · COMPLETED · 20.5k tokens · 1m42s`

### Expanded view

Show:

- Codex decision summary;
- task summary;
- completion summary;
- artifacts;
- duration;
- important statuses;
- links to full detail.

### Pagination and ordering

Default:

- newest first;
- 20 rounds/page.

Support:

- newest / oldest;
- previous / next page;
- configurable page size.

### Live updates

When new events arrive while user is browsing older history:

`New events available — Jump to latest`

Do not forcibly move scroll position.

### Search/filter

Search by:

- MESSAGE_ID;
- TASK_ID;
- STAGE_ID;
- keyword;
- artifact name when practical.

Filters include:

- Codex Decision;
- Codex → ZCode;
- ZCode → Codex;
- Human Intervention;
- Deep Review;
- HUMAN_REVIEW;
- Warning;
- Error;
- Complete.

## 12. Task Detail Drawer

Clicking a task opens a drawer instead of navigating away.

Tabs:

- Overview
- Codex Full Dispatch
- ZCode Feedback
- Artifacts
- Context
- Protocol Details

Codex Full Dispatch must show the exact v1.2 archived `TO_ZCODE` content.

Protocol Details may expose MESSAGE_ID, TASK_ID, STAGE_ID, ATTEMPT, NONCE, hashes, claim/fence/archive/seal details.

## 13. Human Control

Primary controls:

- Safe Pause / Resume
- Human Intervention
- Deep Review
- More

Under More:

- Interrupt Current Task
- Formal STOP

High-risk actions require confirmation.

### Safe Pause semantics

Preserve v1.2 semantics.

If ZCode is running:

- current valid task may finish;
- completion stays valid;
- Runtime stops before subsequent normal progression.

If Codex is thinking:

- do not kill the model call mid-turn;
- let the turn finish;
- do not allow stale/unseen work to proceed after Pause wins the control boundary.

If a task is authorized but unclaimed:

- prevent new acquisition according to v1.2 semantics;
- preserve history;
- enter PAUSED.

The UI must explain the expected effect before/after Pause.

## 14. Human Intervention

Form fields:

### Target

- Current Project
- Current Task
- Historical MESSAGE_ID

### Mode

- STEER — user knows what should change
- Deep Review / AUDIT — user suspects a problem and wants Codex to inspect before deciding

### Handling running work

Default:

- let current valid task finish, then apply intervention

Optional:

- interrupt current task and replan

Intervention lifecycle must remain visible: queued → delivered → consumed.

## 15. Pending Controls

Always show outstanding control actions, e.g.:

- Pause requested — waiting for MESSAGE 700126 completion
- STEER H-004 queued for next Supervisor turn
- AUDIT H-005 delivered
- model change queued for next turn

## 16. Interrupt Current Task

Confirmation must explain that this:

- revokes Runtime authority using existing fencing;
- preserves historical records;
- requires future work to use fresh authorization.

It does **not** guarantee instant OS-level process termination.

## 17. Formal STOP

STOP is terminal and distinct from Pause.

Hide it under a secondary/high-risk menu and require explicit confirmation.

Explain that ordinary Resume will not silently resurrect STOPPED work.

## 18. HUMAN_REVIEW UI

When HUMAN_REVIEW occurs, show in plain language:

- why automation stopped;
- whether any task is still authorized/running;
- whether data/history are safe;
- what the user can do next.

Provide:

- View Full Reason
- Submit Human Decision

Do not force the user to inspect raw JSON.

## 19. Project COMPLETE UI

Show:

- Final Verification status;
- total duration;
- Supervisor turns;
- Executor tasks;
- revisions/retries;
- human interventions;
- Codex token usage;
- final artifacts;
- links to Timeline and Artifact Center.

History remains inspectable after completion.

## 20. Artifact Center

Artifact Center is a dedicated page/workspace.

### v1.3.0 preview formats

Support:

- Markdown;
- TXT;
- LOG;
- common code files;
- PNG;
- JPG/JPEG;
- WebP;
- CSV;
- JSON;
- PDF.

Unsupported/binary files still show metadata and may offer local-open actions where appropriate.

### Views

- file tree;
- searchable/filterable list;
- image gallery where useful;
- preview pane;
- provenance panel.

### Filters

- type;
- MESSAGE_ID;
- task;
- status;
- path/root;
- keyword.

### Provenance

Show when available:

- path;
- producing MESSAGE_ID;
- task/stage;
- producer;
- created/published time;
- publication status;
- completion/seal status;
- Final Verification relationship;
- later known references.

### Read-only by default

Allow preview, inspection, open, reference, and Agent-mediated revision.

Do not silently edit Runtime artifacts in-browser and bypass the audit chain.

### Artifact-triggered feedback

From any artifact:

- Give feedback to Codex
- Ask Codex to Deep Review this result

Automatically bind Project + MESSAGE_ID + artifact path + user comment + mode.

Do not automatically dump the entire artifact/project history into the prompt.

If straightforward, allow one feedback item referencing multiple selected artifacts.

Advanced diff/version comparison is deferred to v1.3.1.

## 21. Recent Artifacts in Cockpit

Show a compact Recent Artifacts block with preview/open actions and **View all artifacts**.

Timeline artifact links should open Artifact Center already filtered to the relevant MESSAGE_ID/artifact.

## 22. Token Usage

Displaying usage itself must not require additional AI calls.

Record per Supervisor turn where available:

- model;
- reasoning effort;
- input tokens;
- output tokens;
- total tokens;
- duration.

Project summary:

- project total;
- turn count;
- average per turn;
- highest-cost turn;
- recent usage.

If ZCode usage is not reported, explicitly show `Not reported`; never invent values.

Mechanically flag unusually expensive turns relative to recent average.

## 23. Runtime Health and Soft Alerts

Show:

- Web Console backend;
- Orchestrator;
- Codex state;
- ZCode last observed activity;
- current authorization;
- current claim;
- pending interventions;
- errors/warnings.

Soft-alert examples:

- ZCode pickup taking unusually long;
- authorization nearing expiry;
- Codex turn unusually long;
- completion committed but not consumed within expected time;
- Runtime offline.

Distinguish informational / warning / needs-attention.

## 24. Notifications

Do not notify on every normal Agent event.

Optional informational notifications:

- COMPLETE;
- safe Pause reached;
- prolonged ZCode pickup;
- high token turn.

Must-attention notifications:

- HUMAN_REVIEW;
- ORCHESTRATOR_ERROR;
- severe Runtime health failure;
- important task expiry risk.

Never forcibly navigate the user away from the current Runtime.

## 25. Settings

### Global defaults

- default Supervisor model;
- default reasoning effort;
- default decision-summary mode;
- notification preferences;
- Timeline page size.

### Per Runtime / Project overrides

Project-specific values may override defaults.

### UI-only operator note

Allow a local note that is **not** automatically included in Codex context. Only submit it to Codex when the user explicitly converts it into an intervention.

## 26. Local Web Backend

Frontend must use bounded APIs, not scrape terminal text and not accept arbitrary shell command strings.

Preferred architecture:

`Browser → local Web API → Runtime control-plane functions → Runtime Core`

Explicit operations may include:

- list/register Runtimes;
- get status;
- get Timeline page;
- get Supervisor task;
- get Executor feedback;
- get interventions;
- submit intervention;
- pause/resume;
- interrupt/stop;
- list/preview artifacts;
- model config;
- create/bootstrap project;
- preflight;
- start Runtime.

## 27. Web Console startup

Provide:

- `START_WEB_CONSOLE.ps1`
- `STOP_WEB_CONSOLE.ps1`

Optional Windows shortcut:

- `General Agent Runtime.lnk`

Normal startup:

1. detect existing Console instance;
2. if already running, open it;
3. otherwise start one backend;
4. wait for health;
5. open default browser.

Diagnostic mode may support:

`./START_WEB_CONSOLE.ps1 -Foreground`

Normal desktop launch should not require a visible terminal window.

v1.3.0 listens only on localhost.

## 28. AI/token cost behavior

### No extra model call by default

- Timeline;
- task history;
- feedback history;
- artifact preview;
- context manifest;
- token display;
- Runtime health;
- deterministic alerts;
- search/filter;
- Next Expected.

### Small added output

Compact `decision_summary` is produced during the normal Supervisor turn.

### Explicit extra AI use

- deep explanation of a decision;
- semantic artifact analysis;
- Deep Review/AUDIT;
- STEER requiring new Supervisor reasoning.

UI may label relative AI cost Low / Medium / High without claiming exact future-token values.

## 29. v1.3.0 explicit non-goals

Not included:

- public internet exposure;
- LAN remote control;
- mobile remote-control product;
- user accounts / permissions;
- collaborative editing;
- arbitrary Web Shell;
- direct browser editing of Runtime artifacts;
- direct ZCode Desktop control without a supported API;
- image-region annotation feedback;
- advanced artifact version diff;
- automatic AI analysis of every artifact;
- cloud sync;
- exact future-token cost prediction.

Potential later work (v1.3.1+): richer artifact diffs, side-by-side image versions, region feedback, CSV quick charts, richer analytics, direct ZCode integration if supported, remote/mobile access with authentication, formal human-edit protocol.

## 30. Development isolation

v1.3 should be built by a stable v1.2 Builder Runtime and must not make the active Builder Runtime modify itself.

Recommended separation:

- **Stable Builder Runtime:** runs released v1.2.0 and hosts autonomous Codex + ZCode development.
- **Target source worktree:** separate checkout based on v1.2.0, e.g. `C:\general-agent-runtime-v1.3-dev`.

The Builder Runtime may modify the target source only when project-authorized.

## 31. v1.3.0 acceptance criteria

### Setup

- Console starts from PowerShell.
- shortcut/double-click startup works.
- single-instance behavior works.
- browser opens automatically.
- multiple isolated Runtimes can be registered.
- new project flow works end-to-end.
- Goal Workshop context is generated.
- Goal validation works.
- inputs can be registered.
- Supervisor model/reasoning config works.
- ZCode prompt can be generated/copied.
- preflight works.
- Start launches Runtime.

### Cockpit

- Current state is human-readable.
- Next Expected is shown.
- Timeline updates during real execution.
- collapse/expand works.
- pagination/order/search/filter work.
- exact Codex dispatch is viewable.
- authoritative ZCode feedback is viewable.
- Supervisor context manifest is viewable.
- per-turn token usage is shown when available.

### Human Control

- Safe Pause / Resume work.
- STEER works.
- Deep Review works.
- historical MESSAGE_ID targeting works.
- Interrupt works.
- STOP works.
- Pending Controls are visible.
- HUMAN_REVIEW is understandable and actionable.

### Artifacts

- Artifact Center lists project artifacts.
- supported formats preview correctly.
- artifacts show provenance.
- Timeline links to round artifacts.
- artifact-triggered STEER works.
- artifact-triggered Deep Review works.
- browser is read-only by default.

### Lifecycle

- COMPLETE / Final Verification are clearly shown.
- HUMAN_REVIEW / ERROR are clearly shown.
- history remains available after completion.

### Multi-Runtime isolation

- switching Runtime shows correct isolated data.
- one Runtime cannot mutate another through the Web Console.
- alerts identify the correct Runtime.

### Backend/API

- frontend does not scrape PowerShell screen output.
- no arbitrary-shell API is required.
- machine responses are bounded and Unicode-safe.

### Release validation

Before v1.3.0 release:

- backend/frontend automated tests pass;
- existing v1.2 Runtime regression suite remains green;
- clean-install Web Console startup test passes;
- release-like black-box acceptance passes;
- real Codex ↔ ZCode project runs under Web Console supervision;
- Pause / intervention / artifact inspection are exercised in dogfood;
- no regression of v1.2 control-plane safety gates is observed.

## 32. Product definition

> **General Agent Runtime v1.3 turns the v1.2 control plane into a local visual Agent operations console: create projects, configure Codex and ZCode, start and monitor multiple isolated Runtimes, inspect every Supervisor/Executor exchange and artifact, observe per-turn context and token usage, and safely intervene without using PowerShell for routine operation.**

The experience should feel like operating a transparent Agent cockpit, not watching opaque terminals and giant JSON logs.
